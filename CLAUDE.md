# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Mortimer (internal package name `jarvis`) is a local-first voice AI agent: speech in, agentic reasoning, speech out. A single voice-facing **Supervisor** LLM understands intent and delegates to five text-only sub-agents (Scheduler, Librarian, Analyst, Systems, Developer), each backed by one or more MCP skill servers running as separate processes. State is local SQLite; the only cloud dependencies are the speech/LLM/search APIs (and GitHub, if app-development or self-edit features are enabled).

*(`jarvis/` and all `JARVIS_*` env vars are stable internal identifiers — do not rename them. Everything user-facing says "Mortimer".)*

## Architecture

```
Browser (React/Vite) --WebRTC--> Python bot (Pipecat pipeline) --MCP/stdio--> MCP skill servers
```

**Bot pipeline** (`jarvis/bot/pipeline.py`): `SmallWebRTCTransport` audio in → Silero VAD → `DeepgramFluxSTTService` → context aggregator → `OpenAILLMService` (Supervisor brain, any OpenAI-compatible Chat Completions endpoint with function calling) → `ElevenLabsTTSService` → audio out. Tool calls from the LLM go through the MCP tool layer or `delegate_task(agent, task)`.

**Delegation model**: the Supervisor never calls skill tools directly for delegated domains — it calls `delegate_task`, which hands the task to a `SubAgent` (`jarvis/agents/base.py`, `delegate.py`, `supervisor.py`), which in turn only has access to the MCP servers listed for it in `config/agents.yaml`. This routing config is the single source of truth for "who can do what" — read it before assuming a capability lives elsewhere. `jarvis/prompts.py` is the single source of truth for all system prompts (Supervisor, sub-agents, voice addendum); look there before searching for prompt text elsewhere.

**Tool-result honesty** (`jarvis/toolresult.py`, MORTIMER_AGENT_TRUST_PLAN.md Part A): `classify_tool_result(tool_name, result_str)` is the single shared judge of whether a tool call actually succeeded — imported by both `SkillRegistry.call()` (the `mcp_call` event's `ok` flag) and `SubAgent._loop` (the `tool_result` event's `ok` flag and the anti-fabrication logic below), so the transport layer and the sub-agent loop can never disagree about the same call. A failed tool result gets a `role: "system"` constraint message injected immediately after it, forbidding the model from inferring or describing data it never actually retrieved; if every tool a run attempted failed (`tools_attempted > 0 and tools_failed == tools_attempted` — deliberately not on partial failure), the run's reply is overridden rather than left to the model's own wording. Do not reintroduce a second, independent "did this succeed" heuristic anywhere in the tool-call path — that duplication (a transport-level `ok=1` alongside a body that says `{"error": ...}`) is what let a 401 get reported to a user as "the sidecar may be offline."

**MCP skill servers** (`mcp_servers/*/`, each with `logic.py` + `server.py`): `mcp_time`, `mcp_notes`, `mcp_reminders`, `mcp_web`, `mcp_system`, `mcp_git`, `mcp_apps`, `mcp_repo`, `mcp_selfedit`. Convention: `logic.py` is pure/testable (network or DB clients injected), `server.py` wires it up as a FastMCP server over stdio. The registry (`jarvis/skills/registry.py`, driven by `config/mcp_servers.yaml`) spawns these as subprocesses and exposes their tools to the bot. `mcp_repo` (`repo_read_file`/`repo_list_files`/`repo_search`/`repo_write_file`/`repo_commit_write`) is deliberately a separate server from `mcp_apps`: `mcp_apps` is GitHub-only (only `mcp_apps/github.py` touches the network); `mcp_repo` is the local working tree on this machine, path-confined by `resolve_repo_path` (deny-lists for both readable and, separately, writable paths — `.git`/`.env`/secrets/config/CI/lockfiles) and gated by the same draft→confirm `actions`-table pattern `mcp_git` uses for commits. Every tool description on both servers states which one it is ("Local working tree on this machine:" vs "GitHub:") because tool selection happens off the schema text, not off `config/agents.yaml` alone (`MORTIMER_AGENT_TRUST_PLAN.md` D13/D14).

**Self-development loop**: Mortimer can propose edits to its own UI/config, by voice or via the web console's Edit panel. `jarvis/admin/server.py` (the admin sidecar, `:7861`) is the single owner of the self-edit service (`jarvis/selfedit/service.py`); `mcp_selfedit` and the console's Edit panel are both thin HTTP clients of that sidecar — don't duplicate self-edit logic in either. Edits are confined to `config/self_edit_allowlist.json` (deny list always wins; never wake word, agents, CI, dependencies, or the self-edit machinery itself), land on `jarvis/self-edit/*` sandbox branches with a rollback tag, must pass validation (allowlist check, backend import, frontend build) before a PR, and merging always happens on GitHub by a human — Mortimer cannot merge. Planner models for this loop are named profiles in `config/upgrade_models.yaml` (not itself on the allowlist, so the agent can't repoint its own brain); loop bounds (max iterations/minutes) are in `config/upgrade_agent.yaml`.

**App-development**: `mcp_apps` lets the Developer sub-agent scaffold a new private GitHub repo per app (only after user confirmation), tracked in an app registry on the `mortimer-dev` branch. Only `mcp_apps/github.py` should touch the network; `logic.py` takes an injected client, matching the pattern used across the other MCP servers.

**LLM Council** (`jarvis/council/`, MORTIMER_LLM_COUNCIL_PLAN.md, superseded/extended by MORTIMER_LLM_COUNCIL_V2_PLAN.md): a council may rank, review, and advise on the self-edit loop — it may NEVER author a merged artifact. Every diff reaching `session_validate` is still written whole by exactly one model; the council only ever produces a prose brief. `scoring.py` and `config.py`'s pure helpers import nothing from `openai`/`jarvis.selfedit`/`jarvis.agents`, so the selection math is unit-testable without network; `council.py` is the only module that talks to models or the database. Convening is **never predictive** — the automatic triggers are `UpgradeAgent`'s E1 (`_maybe_escalate` in `jarvis/agents/upgrade_agent.py`: validation failed twice, the single repair attempt also failed) and E2 (V2 V14: the agent declines an off-allowlist goal — `_maybe_scope_council` convenes a tier-1, advisory-only, at-most-once-per-run "scope advisor" council with its own `SCOPE_ADVISOR_PROMPT`/`SCOPE_JUDGE_PROMPT` and `placement="scope"`; it never touches `_escalations_used`, so it can't itself trigger tier-2 escalation math), plus the admin sidecar's manual `POST /api/council/convene` and `POST /api/selfedit/reject` (E3). A second escalation (tier 2) also carries the tier-1 winner forward as an extra candidate proposal (V2 V1: `UpgradeAgent._last_council_winner`, consumed via `context["carry_forward"]`) and, on success, extends the run's iteration budget by `COUNCIL_RETRY_EXTRA_ITERATIONS` (V2 V10) rather than letting the extra attempt eat into the original budget. Cost rises only after demonstrated difficulty: tier 1 (first escalation) fans out to all `economy` profiles as proposers and all `mid` profiles as judges — with a V2 V8 backfill (`COUNCIL_JUDGE_TARGET = 2`) walking the tier ladder upward from `mid` into `frontier` judges when `mid` alone can't field at least two usable judges; tier 2 (a second escalation) adds `frontier` proposers and judges with `frontier` only — **not** `mid`, a deliberate deviation from the plan's original table (`jarvis/council/config.py`'s `TIER_MEMBERS` comment) made to keep proposers and judges disjoint (a model never scores its own proposal) even where tier NAMES would otherwise overlap; `resolve_members`'s `exclude` parameter enforces this per-member, not just per tier name. `COUNCIL_MAX_ESCALATIONS = 2`, tiers strictly ascending, never repeating — a third failure ends the session exactly as it did before this feature existed. Every judge scores every proposal 1.0–10.0 in tenths (`scoring.py`'s `parse_scores`, using V2 V6's stricter regex — `7.44` is now an abstention, not a `7.4`-plus-leaked-justification silent misparse); an unparseable or out-of-range score is an explicit abstention, never silently dropped, matching `jarvis/toolresult.py`'s "never infer from prose what can be recorded as fact" discipline. Judges also see failure context (V2 V2: the failing diff/checks for a planner round, or the decline reason/allowlist for a scope round) assembled once by `_judge_user_message` and reused identically by `--replay`. Proposal labels (`Proposal A`/`B`/...) are assigned by one function, `_shuffle_and_label` (V2 V4: a deterministic per-round shuffle seeded from `round_id` via SHA256, using a local `random.Random` instance — never the global `random` module — so a judge can't infer a proposal's origin from label order). The winner is picked deterministically (`select_winner`: highest mean → highest min → lowest variance → registry order) and is a **proposal**, never "the best model" — identity is unmasked only after selection; the registry order used for that final tiebreak is persisted per round (`council_rounds.registry_order`, V2 V13) so `--agreement`/`--replay` tiebreak against the registry *as it was*, not as it is today (pre-V2 rounds fall back to the old row-order approximation). Every round is logged to `council_rounds`/`council_scores` (migration `0009_council`, extended by `0010_council_v2` for `prompt_tokens`/`completion_tokens`/`registry_order`, both in `jarvis/db.py`) plus a full JSONL payload under `logs/council/<date>/<round_id>.jsonl`, mirroring the run-log's two-tier pattern; `retry_validated` records whether the post-council retry actually passed; token usage (when a provider reports it) rolls up into the round row and a summary line in `--agreement`, NULL rather than 0 when unknown (V2 V9). `council_rounds.run_id` is reserved, not wired up: it stays NULL for every self-edit round because the sidecar's `UpgradeAgent` has no voice-path `run_id` to correlate against — a deliberate non-decision (V2 V12), not a bug, left for a future workflow (e.g. apps) that runs inside the bot process. Judge-tier quality (can a cheaper `mid` judge be trusted?) is measured, not assumed: `should_shadow` deterministically (SHA256 of `round_id`, not `random()`) samples a fraction of tier-1 rounds for an additional advisory `frontier` judge pass; as of V2 V7 this shadow pass runs **off the live path**, on its own detached daemon thread with its own `asyncio.run(_shadow_pass(...))` (`COUNCIL_SHADOW_INLINE` is a test-only knob to force it synchronous), so it can never delay `convene()`'s return — shadow score rows land with `shadow = 1` and are appended to the round's JSONL afterward, and are **never** consulted by `select_winner`; every read path filters `WHERE shadow = 0` before selecting. `python -m jarvis.council --replay <round_id> --judges frontier` re-scores a stored round's proposals retroactively (read-only; writes only `shadow=1` rows, or nothing with `--dry-run`), and `python -m jarvis.council --agreement [--since 30d]` reports winner agreement (the primary metric — selection only ever consumes the winner, not raw scores), rank correlation, abstention rate, discrimination by judge tier, and a token-usage summary, then states which promotion branch applies. Promotion thresholds (`COUNCIL_AGREEMENT_MIN_ROUNDS`/`_FLOOR`/`_ABSTENTION_CEILING`/`_DISCRIMINATION_FLOOR` in `jarvis/council/config.py`) are fixed in advance, not hand-tuned after looking at data; fewer than 20 shadowed rounds always means "insufficient data, keep mid-tier," never a judgment call on a small sample — which is also why council retention (`JARVIS_COUNCIL_RETENTION_DAYS`, default 180, V2 V11) is deliberately much longer than the run-log's 30 days: pruning faster than shadowed rounds accumulate would permanently starve that measurement. `config/upgrade_models.yaml` (with its new `tier:` field per profile) stays off the self-edit allowlist — the council's UI membership picker (`EditModePanel.tsx`, `mortimer.council.<tier>` in `localStorage`, matching the drawer's `mortimer.drawer.*` convention) can only narrow which *existing* profiles participate, never define a new endpoint or key. `POST /api/council/convene` and the E3 half of `POST /api/selfedit/reject` no longer block the request for the full round (V2 V5): they validate synchronously, then hand the round to the same `_council_job`/`_council_lock` background-thread-plus-polling shape `_run_job` already uses for self-edit runs, and return immediately (`{"ok": true, "started": true}` / `{"ok": true, "reverted": ..., "council_started": bool}`); `GET /api/council/job` is the polling target. `EditModePanel.tsx` polls that endpoint every 3s (mirroring its existing self-edit run polling) and, once a round settles, both renders the winner card and lets the user expand a "Recent rounds" `<details>` block (`GET /api/council/rounds?limit=10`, V2 V12) to reach any round — including E1 rounds, which happen inside a background agent run and would otherwise be invisible without the CLI. `JARVIS_COUNCIL_ENABLED=false` is the kill switch, enforced at exactly one point (the top of `convene()`) — disabling it costs nothing and escalation falls through to the pre-council report-and-stop behavior unchanged. App-scaffolding has no council integration yet (`mcp_apps` has no validation gate to escalate from) — the module is workflow-agnostic so this can be added later without redesign, but do not invent a trigger for it.

**Voice UI control** (`jarvis/bot/ui_control.py`, `web/src/uiCommands.ts`, MORTIMER_VOICE_UI_PLAN.md): the console's chrome — side drawer, its six tabs, transcript, display windows, mic mute, wake word — is voice-controllable via one Supervisor tool, `ui_control` (the `set_voice` pattern generalized: direct tool, injected side effect, never a delegation). The handler validates and emits one `{"type": "ui", ...}` app message; `App.tsx`'s existing ServerMessage listener forwards it into the `uiCommands.ts` pub/sub store, and each state OWNER (App for drawer/transcript, `DisplayPanel` for display windows, `MicControls` for mic/wake) applies only its own actions through the SAME setters its buttons call — voice and click can never diverge. The bot holds no UI state. Feedback is hybrid (U5, prompt addendum `UI_CONTROL_ADDENDUM` in `jarvis/prompts.py`): silence when something visibly changes; when nothing changes the client sends `{"type": "ui/noop", "reason": ...}` and the bot speaks the reason VERBATIM via `TTSSpeakFrame` — deliberately no LLM in that path (the tool already returned, canned TTS is immediate and can't trigger further tool calls). There is deliberately no `mic_unmute` (while muted the user can't be heard; the wake word is the way back). Display mode is implicit: a live popup (`displayWindow.ts`'s `hasLivePopup()`) means dual-screen — informational payloads go there; otherwise they render in the in-page frosted overlay (max 40vw/40vh, persistent until dismissed, no auto-timeout). `JARVIS_UI_CONTROL_ENABLED=false` is the kill switch, enforced at the single registration site in `pipeline.py` (tool unregistered + prompt addendum omitted; buttons unaffected). Routing-eval cases pin that UI utterances are never delegated to developer — rule 8's "changing your own interface" means code changes, not view changes.

**Wake word** (optional, fully local): `jarvis/wakeword/` — `logic.py` (`WakeGate`: pure threshold/cooldown logic), `server.py` (localhost websocket sidecar, `:7862`), `train.py` (trains a custom ONNX model from `say`-generated samples, no cloud). Client hook is `web/src/wakeWord.ts`.

**Console side drawer** (`web/src/components/SideDrawer.tsx`, `web/src/sidedrawer.css`, MORTIMER_SIDE_DRAWER_PLAN.md): the four console panels (Repo/Edit/Memory/Runs) plus a Developer run-status tab and an Output tab all live in one right-side tabbed drawer that *pushes* the stage (`.stage-row` is a flex row wrapping `.main` and the drawer) rather than covering it; width is drag-resizable and, with open state and active tab, persisted in `localStorage` under `mortimer.drawer.*`. **Naming rule: this is the side *drawer*, never a "sidecar"** — in this codebase "sidecar" already means the admin Python process on `:7861` (`jarvis/admin/server.py`, `JARVIS_ADMIN_URL`), the same word-reuse discipline as "procedure" vs "skill". Live sub-agent run state lives in the module-level store `web/src/agentRuns.ts` (publish/subscribe, same shape as `agentLayout.ts`) because the drawer's tab bodies unmount on every tab switch and close; `AgentStatusPanel` is the single registrant of the RTVI `ServerMessage` listener that feeds it, and it renders only non-Developer runs (Developer runs go to the drawer tab, with a live indicator on the topbar `🛠 Dev` button so a self-edit is visible even when the drawer is shut).

**Display payloads split by surface** (`jarvis/bot/display.py`'s `DISPLAY_SURFACE`, `web/src/displayResults.ts`, `web/src/displayWindow.ts`, MORTIMER_SIDE_DRAWER_PLAN.md D28/D36): a sub-agent tool result is routed server-side, per tool, to one of two places — work product (diffs, commits, app scaffolds) goes to the drawer's Output tab (`OutputTab.tsx`, a bounded newest-first collapsible list, kept in the module store `displayResults.ts`); an informational answer (weather, research, radar) keeps the floating `DisplayPanel.tsx` window and can additionally be popped out (`⧉`) into a real second browser window (`display.html`, a **separate Vite entry** — `displayMain.tsx` must never import `jarvisClient.ts`, whose module-load side effects patch `getUserMedia` and construct a `PipecatClient`) relayed via `BroadcastChannel("mortimer.display")` in `displayWindow.ts`, so it can be parked on a second monitor. All three consumers (`DisplayPanel`, `OutputTab`, the popup's `DisplayWindowApp`) share one rendering component, `DisplayContent.tsx`. A missing/unrecognized `surface` defaults to the drawer (the less intrusive outcome).

**Credential vault** (`jarvis/vault.py`, MORTIMER_CREDENTIAL_VAULT_PLAN.md): credentials live in `data/secrets.vault` (AES-256-GCM; master key in the macOS Keychain, or `JARVIS_VAULT_KEY` for headless/CI), not in `.env` — `.env` holds configuration only after `python -m jarvis.vault migrate`. The environment stays the transport: `inject_env()` copies vault secrets into `os.environ` at exactly four call sites (top of `load_settings()`, module top of `jarvis/admin/server.py`, and guarded imports in `scripts/check_env.py` and `scripts/check_skills.py`'s `main()`) before anything reads them, so pydantic `Settings`, the registry's `${VAR}` expansion for MCP child processes, and `UpgradeAgent`'s direct env reads never know the vault exists. Precedence: a non-empty env var beats the vault (CI/override channel); an *empty* env var loses to it (the run scripts' `set -a; . ./.env` exports blank `NAME=` lines as `""`, which must not shadow real values). Missing vault = silent fallback to `.env` (fresh checkouts work unchanged); present-but-unreadable vault = hard error, never a half-configured run. Management is CLI-only (`python -m jarvis.vault`) — deliberately no console panel, no admin endpoint, no MCP tool, so secrets never transit the LLM or the browser; `jarvis/vault.py`, `data/**`, and `*.vault` are on the self-edit deny list and `*.vault` is read-denied in `mcp_repo`, same never-touch-your-own-credential-machinery rule as `config/upgrade_models.yaml`. `JARVIS_VAULT_ENABLED=false` is the kill switch, enforced only inside `jarvis/vault.py`. Future integrations (e.g. Gmail OAuth refresh tokens) write back via `set_secret()` — do not invent a second storage path for new credentials.

**Config vs. code boundary**: routing (`config/agents.yaml`), server wiring (`config/mcp_servers.yaml`), voices (`config/voices.yaml`), and self-edit bounds/allowlist are all YAML/JSON, not Python — check config first when a behavior seems misrouted or over/under-permissioned rather than assuming it's hardcoded.

**Run log** (`jarvis/runlog/`, MORTIMER_RUN_LOGGING_PLAN.md): every `delegate_task` call gets a `run_id`, generated in `jarvis/agents/delegate.py` and threaded through `SubAgent.run()` (`jarvis/agents/base.py`) down to each MCP call in `SkillRegistry.call()` (`jarvis/skills/registry.py`) via a `contextvars.ContextVar` holding the live `RunLogger` instance (not just the id — this is what lets an MCP-layer failure land in the same record as the sub-agent's own tool call). Each run writes one `agent_runs` row plus N `agent_events` rows (bounded previews, migration `0006_agent_runs` in `jarvis/db.py`) and one untruncated JSONL payload file under `logs/agents/<date>/<run_id>.jsonl`. Review with `python -m jarvis.runlog`, the admin sidecar's `GET /api/runs`/`GET /api/runs/{run_id}`, or the console's Runs panel — all three read the same `jarvis/runlog/store.py` helpers, so they can't disagree. `JARVIS_RUNLOG_ENABLED=false` is the kill switch; `JARVIS_RUNLOG_RETENTION_DAYS` controls pruning, applied once at bot startup. Two per-run counters, `tools_ok`/`tools_failed`, are derived inside `RunLogger` itself from the same tool-result classification (`jarvis/toolresult.py`'s `classify_tool_result` — the one shared judge of "did this tool call actually succeed", used by both `SkillRegistry.call()`'s `mcp_call` event and `SubAgent._loop`'s own tool-result handling, so the two layers can never record contradictory verdicts for the same call); NULL on pre-migration rows, never backfilled, readers fall back to `tool_count`. Also at bot startup, alongside the retention prune: `reconcile_orphaned_runs()` rewrites any `agent_runs` row still `status='running'` (from a process that died without finishing) to `status='orphaned'` if it's older than `RUN_ORPHAN_AFTER_S` — nothing is running yet at that point in boot, so anything left `running` is definitionally dead.

**Procedures** (`jarvis/procedures.py`, MORTIMER_MEMORY_PROCEDURES_PLAN.md Part B — never call this concept a "skill"; that word already means "an MCP server" elsewhere in this codebase, see `mcp_servers/*/skill.yaml`). After a delegation finishes, `jarvis/agents/delegate.py` spawns `learn_from_run()` as a fire-and-forget background task: it matches the run's task against existing procedures for that agent (SQLite FTS5 candidate generation over `procedures`/`procedures_fts`, migration `0007_procedures`, plus a Python-side token-overlap score — no embeddings) and either reinforces a match's success/failure counters or, only for a run that actually succeeded with no match, creates a new `candidate` procedure via one small LLM call. A candidate becomes `active` after `PROCEDURE_PROMOTE_AFTER` net successes and stays eligible to be injected as a hint until failures start to outweigh successes, at which point it's `deprecated` (counters keep updating; status never auto-reverts). At the start of a delegation, `SubAgent._loop` runs the same matching function against `active` procedures only and, on a match, injects one short `system`-role hint message before the task. A procedure is a hint only — its description is free text describing what worked, never a replay mechanism, and no confirmation gate is touched by this feature (true by construction: the hint is a prompt message, not a code path). `JARVIS_PROCEDURES_ENABLED=false` is the kill switch, enforced once inside `jarvis/procedures.py` itself. Matching is task-shape-to-task-shape (`MORTIMER_AGENT_TRUST_PLAN.md` D21/D22): each candidate stores `task_tokens` — the stopword-filtered tokens of the task that created it, written once by `_create_candidate` — and `match_procedure` scores the incoming task's tokens against `task_tokens` (never against `label`/`description`, which is what the hint text still is), using a symmetric overlap ratio (`len(a & b) / min(len(a), len(b))`) so containment scores 1.0 regardless of which side is longer. Rows from before migration `0008` have `task_tokens = ''` and are permanently unmatchable by design (not backfilled — deriving tokens from a summary is the exact vocabulary mismatch this fixed); `DELETE FROM procedures WHERE task_tokens = '' OR task_tokens IS NULL;` is the recommended (not automatic) operator cleanup. `PROCEDURE_MATCH_THRESHOLD` is not hand-tuned — `python -m jarvis.procedures --calibrate` computes it deterministically from the logged run corpus (MATCHED/UNMATCHED score populations by tool-sequence equality, a three-branch percentile rule, clamped to `[0.20, 0.60]`); `--explain "<task>" [--agent NAME]` shows every stored procedure's score and shared tokens against a task for debugging a missed or unwanted match.

## Testing conventions

- `tests/unit/` — one file per module, no external calls, mirrors `logic.py`/service structure.
- `tests/integration/` — MCP-over-stdio, registry wiring, bot wiring; some marked `live` (real external APIs, opt in with `RUN_LIVE=1`).
- `tests/evals/routing_eval.py` — live LLM eval of Supervisor routing accuracy; must stay ≥ 90%.
- `tests/acceptance/` — manual scripted checklists per implementation phase, not run by pytest.
- `pytest.ini` sets `asyncio_mode = auto`, so async test functions don't need `@pytest.mark.asyncio`.

## Known deviations and gotchas
