# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Mortimer (internal package name `jarvis`) is a local-first voice AI agent: speech in, agentic reasoning, speech out. A single voice-facing **Supervisor** LLM understands intent and delegates to five text-only sub-agents (Scheduler, Librarian, Analyst, Systems, Developer), each backed by one or more MCP skill servers running as separate processes. State is local SQLite; the only cloud dependencies are the speech/LLM/search APIs (and GitHub, if app-development or self-edit features are enabled).

*(`jarvis/` and all `JARVIS_*` env vars are stable internal identifiers — do not rename them. Everything user-facing says "Mortimer".)*

## Architecture

```
Browser (React/Vite) --WebRTC--> Python bot (Pipecat pipeline) --MCP/stdio--> MCP skill servers
```

**Bot pipeline** (`jarvis/bot/pipeline.py`): `SmallWebRTCTransport` audio in → Silero VAD → `DeepgramFluxSTTService` → context aggregator → `OpenAILLMService` (Supervisor brain, any OpenAI-compatible Chat Completions endpoint with function calling) → `ElevenLabsTTSService` → audio out. Tool calls from the LLM go through the MCP tool layer or `delegate_task(agent, task)`.

**Delegation model**: the Supervisor never calls skill tools directly for delegated domains — it calls `delegate_task`, which hands the task to a `SubAgent` (`jarvis/agents/base.py`, `delegate.py`, `supervisor.py`), which in turn only has access to the MCP servers listed for it in `config/agents.yaml`. This routing config is the single source of truth for "who can do what" — read it before assuming a capability lives elsewhere. `jarvis/prompts.py` is the single source of truth for all system prompts (Supervisor, sub-agents, voice addendum); look there before searching for prompt text elsewhere.

**Per-run model requests** (`MORTIMER_GATE_V2_AND_MODEL_REQUEST_PLAN.md` F6-F9, 2026-08-22, Larry: named-model requests like "do this one with Opus" were previously either ignored or silently run on whatever the agent's own `model_profile:` default was): `delegate_task` gained an optional `model_profile` argument, resolved through the SAME model registry every other resolution path uses (`SubAgent.resolve_model_profile`, reusing `load_model_registry`/`resolve_profile` exactly as `__init__` does) — never a second registry, never a second lookup path. Resolution and the completion call are both LOCAL to that one `run()` invocation (`model_profile_override` threaded through `run()`/`_loop()` as parameters, never written to `self._client`/`self._model`) because barge-in survival runs delegations as detached tasks, so two concurrent `run()` calls can be in flight on the same `SubAgent` instance at once — a per-run override written to instance state would leak into the other call. An explicit request always REFUSES on resolution failure — never silently falling back to a different model — regardless of that agent's own configured `on_profile_fallback` (`warn` vs `refuse`), because that setting governs the agent's own infrastructure default, not a request the user stated by name; `delegate.py`'s handler resolves the override and returns `REFUSED: ...` before any run row, retry-guard entry, or `agent.run()` call happens at all. On success, the reply gets a code-appended `\n[ran on <model>]` suffix (mirroring the `ITERATIONS_EXHAUSTED_MESSAGE`/`TOOL_FAILURE_CONSTRAINT_TEMPLATE` mechanical-backstop pattern — grounded by construction, not by prompt instruction alone) so the Supervisor can honestly report which model actually ran; Supervisor rule 8 maps spoken model names (Claude/Fable/Opus/Kimi/GPT) to their registry profile names and requires waiting for the tool result before naming a model, and the developer's own prompt carries one sentence ("Named-model tasks already ran on that model") so it doesn't discuss availability for a request it already fulfilled.

**Model discipline** (MORTIMER_MODEL_DISCIPLINE_AND_MAC_SHELL_PLAN.md Part A, 2026-08-17): the voice model (a small, cheap model — Haiku today) is a dispatcher, never a design/build model. `config/agents.yaml` entries gain an optional `model_profile:` naming a profile in `config/upgrade_models.yaml` (the ONE model registry, reused via `jarvis/agents/upgrade_agent.py`'s `load_model_registry`/`resolve_profile` — never a second registry); `SubAgent.__init__` resolves it into a real client and model string, falling back to the voice model with a logged warning on any resolution failure (unknown profile, missing API key) — voice must still boot on a fresh checkout with one key. An injected `client_factory` (the test seam) always wins and skips profile resolution entirely. `developer` runs `model_profile: kimi-k3` by default; conversational agents (scheduler/librarian/analyst/systems) stay unset (Haiku is correct for them). The resolved model is what `RunLogger` records, never the configured name, so a fallback is visible in the run log. Two more pieces close the same gap: `docs/REPO_MAP.md`, injected into an agent's system prompt when its `agents.yaml` entry sets `inject_repo_map: true` (construction-time read, 8000-char cap, missing file skipped silently) — a maintained "where things live" map so the developer stops burning its 5-iteration budget rediscovering its own codebase; and a two-layer stop rule after a failed delegation — `SUPERVISOR_PROMPT` rule 11 asks the model not to retry a failed task reworded, and `jarvis/agents/delegate.py`'s mechanical retry guard backs it up: a same-agent delegation within `RETRY_GUARD_WINDOW_S` (120s) of a failure, whose task text overlaps the failed one at `RETRY_GUARD_OVERLAP` (0.5, via `jarvis.procedures`'s existing symmetric token-overlap scorer — one implementation, not a second one), is refused mechanically with a `REFUSED:` string rather than run; a success for that agent clears its guard entry. Model-selection assurance is deliberately NOT a council-per-task (the council's founding rule: convening is never predictive) — assurance comes from this deterministic tier assignment, the existing E1 escalation council when an assigned model demonstrably fails validation twice, and the run log's `model` column for periodic tuning.

**Golden Rules** (`jarvis/prompts.py`'s `GOLDEN_RULES`, Larry 2026-08-18): three short rules concatenated onto the FRONT of `SUPERVISOR_PROMPT` at definition time — never a format placeholder, so a call site cannot omit them. They CONSOLIDATE anti-fabrication language that was scattered across rules 3/11 and the D6/D7 addendum rather than adding to it. The reason they exist is instructive: the old rule 3 ended "and suggest the fix" and rule 11 said "report the sub-agent's stated reason", and when a sub-agent returned the bare `STUCK_MESSAGE` with neither, the model resolved the conflict by inventing "the codebase access is blocked". The prompt did not fail to constrain the model — it instructed it to speculate. So rule 3 now says suggest a fix ONLY if the specialist named one, rule 11 explicitly authorizes "it didn't finish and didn't say why", and Golden Rule 1 states that "I don't know why" is always an acceptable answer. Every rule names its mechanical backstop in the comment above the block, because a rule without a backstop is a wish — the fix that actually closed this hole was `ITERATIONS_EXHAUSTED_MESSAGE`, not the exhortation.

**Iteration budget and honest exhaustion** (Larry 2026-08-18, from two observed runs): the sub-agent loop's cap — not the timeout — was the real wall behind "Mortimer says it can't access things." Runs `54b62f69` and `9f0684e2` read 9-11 files with every tool call SUCCEEDING, hit `MAX_TOOL_ITERATIONS = 5`, returned the generic `STUCK_MESSAGE`, and the Supervisor — given no reason to relay — told the user "the codebase access is blocked right now," which was pure invention. Two fixes, matching the D6/D7 no-fabrication discipline: (1) `config/agents.yaml` gains an optional `max_iterations:` per agent, read by `SubAgent.from_config` exactly like `timeout_s:` (developer is `15`; conversational agents stay at the default 5 — the developer is the one agent that reads its way to an answer); (2) exhausting the budget now returns `ITERATIONS_EXHAUSTED_MESSAGE` naming the real cause ("ran out of tool-call rounds … Nothing was blocked — the work was incomplete, not refused"), and it only replaces the untouched `STUCK_MESSAGE` default, so a real model reply is never clobbered. If an agent reports an access problem, check the run log's tool results before believing it: a permission failure shows `ok=false` on the tool, an exhausted budget shows all-green tools and a short run.

**Barge-in survival** (`jarvis/agents/delegate.py`'s shielded detached task + `late_delivery`, Larry 2026-08-21: *"me continuing to talk should not kill existing work"*): pipecat cancels an in-flight `delegate_task` function call when the user speaks over it — observed live killing 5 of 9 developer runs mid-flight (one AFTER its repo write had executed), leaving zombie `running` rows the Agents tab showed forever, no spoken result, and a user re-ask that killed the next run too; a retry even prepared a second commit staging 28 unrelated files because nobody knew the first had landed. The handler now runs the sub-agent in a DETACHED task and awaits it through `asyncio.shield`: the voice turn's cancellation lands in the handler, the work runs to completion (run-log terminal status, retry guard, handoff record, `delegate_done`, `learn_from_run` — all inside the detached task), and the finished result is injected into the conversation via `late_delivery["fn"]` (the same `inject_context` channel the reminders watcher speaks through), so Mortimer reports it when it lands. `run_task.cancelled()` distinguishes session shutdown (nothing survives, re-raise) from turn cancellation. Related fix, same morning: a confirmation delegation was burning ~6 rounds re-deriving which draft it was confirming, so Supervisor rule 9 now requires the action_id in the confirmation task and `DEVELOPER_CORE` declares a confirmation task to be ONE call.

**Tool-result honesty** (`jarvis/toolresult.py`, docs/plans/implemented/MORTIMER_AGENT_TRUST_PLAN.md Part A): `classify_tool_result(tool_name, result_str)` is the single shared judge of whether a tool call actually succeeded — imported by both `SkillRegistry.call()` (the `mcp_call` event's `ok` flag) and `SubAgent._loop` (the `tool_result` event's `ok` flag and the anti-fabrication logic below), so the transport layer and the sub-agent loop can never disagree about the same call. A failed tool result gets a `role: "system"` constraint message injected immediately after it, forbidding the model from inferring or describing data it never actually retrieved; if every tool a run attempted failed (`tools_attempted > 0 and tools_failed == tools_attempted` — deliberately not on partial failure), the run's reply is overridden rather than left to the model's own wording. Do not reintroduce a second, independent "did this succeed" heuristic anywhere in the tool-call path — that duplication (a transport-level `ok=1` alongside a body that says `{"error": ...}`) is what let a 401 get reported to a user as "the sidecar may be offline."

**MCP skill servers** (`mcp_servers/*/`, each with `logic.py` + `server.py`): `mcp_time`, `mcp_notes`, `mcp_memory`, `mcp_reminders`, `mcp_web`, `mcp_system`, `mcp_git`, `mcp_apps`, `mcp_repo`, `mcp_runlog`, `mcp_selfedit`. `mcp_memory` (Larry 2026-08-21, "Mortimer should have access to control anything in the interface like the memory panel") is the librarian's voice control of the Memory panel's review queue — `memory_review_list`/`memory_review_resolve`, thin over `jarvis.memory_sweep`'s OWN `list_open_reviews`/`resolve_review` (the same functions the sidecar's endpoints wrap), so voice, console, and sidecar can never disagree about what resolving a review does; the tool description requires the user's explicit choice before any resolve. The same request also put `mcp-screen` on ALL FIVE agents in `config/agents.yaml` (was systems+developer only). Interface CHROME control stays a Supervisor-only direct tool (`ui_control`) by design — sub-agents act on data (reviews, notes, repo), never on the user's windows; a specialist moving windows mid-run would compete with the user for the screen, and routing eval pins that UI utterances are never delegated. Convention: `logic.py` is pure/testable (network or DB clients injected), `server.py` wires it up as a FastMCP server over stdio. The registry (`jarvis/skills/registry.py`, driven by `config/mcp_servers.yaml`) spawns these as subprocesses and exposes their tools to the bot. `requires_env` / `optional_env` together must name **every** environment variable the server reads (directly or through a `jarvis.*` import) that is not in `jarvis/skills/registry.py`'s `BASE_ENV_KEYS`. They are an allowlist, not documentation: after `MORTIMER_SECURITY_HARDENING_PLAN.md` K2, an undeclared variable does not reach the child. Use `requires_env` for a variable with no code default (`check_skills.py` fails if it is unset) and `optional_env` for one that has a default (forwarded if present, never required). `requires_env_dynamic` is for a variable whose *name* is chosen at runtime (only `mcp-screen` today). `mcp_repo` (`repo_read_file`/`repo_list_files`/`repo_search`/`repo_write_file`/`repo_commit_write`) is deliberately a separate server from `mcp_apps`: `mcp_apps` is GitHub-only (only `mcp_apps/github.py` touches the network); `mcp_repo` is the local working tree on this machine, path-confined by `resolve_repo_path` (deny-lists for both readable and, separately, writable paths — `.git`/`.env`/secrets/config/CI/lockfiles) and gated by the same draft→confirm `actions`-table pattern `mcp_git` uses for commits. Every tool description on both servers states which one it is ("Local working tree on this machine:" vs "GitHub:") because tool selection happens off the schema text, not off `config/agents.yaml` alone (`docs/plans/implemented/MORTIMER_AGENT_TRUST_PLAN.md` D13/D14).

**Missing-tool honesty + self-repair** (Larry 2026-08-21: *"the missing tool needs to be acknowledged so that we can fix the issue… self-edit could resolve the issue when I ask"*, after a live session where a tool gap made the Supervisor screen-read its own Memory panel and ask Larry to copy items): Supervisor rule 10 now carries a MISSING-TOOL exception — a specialist reporting it has no tool for the task is relayed plainly, with an offer to have the developer add it, and improvising around a gap (reading own panels via view_screen, asking the user to relay data the system holds) is explicitly forbidden. To make the fix actually reachable by voice, `mcp_servers/**`, `config/agents.yaml`, and `config/mcp_servers.yaml` joined the self-edit allowlist and the developer's self_development section routes capability additions through `selfedit_start`. **This deliberately moves the privilege-escalation gate**: a self-edit can now PROPOSE granting an agent new tools, so the enforcement point is the validation gates plus the human merging the PR on GitHub — which was always the real gate. Still human-only: `config/upgrade_models.yaml` (the agent's own brain), `config/skills.yaml` (the one-at-a-time skill enable rule), `config/upgrade_agent.yaml`, and the allowlist itself.

**Self-development loop**: Mortimer can propose edits to its own UI/config, by voice or via the web console's Edit panel. `jarvis/admin/server.py` (the admin sidecar, `:7861`) is the single owner of the self-edit service (`jarvis/selfedit/service.py`); `mcp_selfedit` and the console's Edit panel are both thin HTTP clients of that sidecar — don't duplicate self-edit logic in either. Edits are confined to `config/self_edit_allowlist.json` (deny list always wins; never wake word, agents, CI, dependencies, or the self-edit machinery itself), land on `jarvis/self-edit/*` sandbox branches with a rollback tag, must pass validation before a PR — allowlist check, backend import, frontend build, and (C2, MORTIMER_MODEL_DISCIPLINE_AND_MAC_SHELL_PLAN.md, 2026-08-17) `pytest tests/unit -q` as a fourth gate, `VALIDATE_PYTEST_TIMEOUT_S = 300` — and merging always happens on GitHub by a human — Mortimer cannot merge. CI's own `Unit tests` step in `.github/workflows/validate.yml` is blocking for the same reason as this fourth gate: a self-edit that imports cleanly and builds the frontend can still break backend behavior, and the self-edit loop and CI must not disagree about what "passing" means. Planner models for this loop are named profiles in `config/upgrade_models.yaml` (not itself on the allowlist, so the agent can't repoint its own brain); loop bounds (max iterations/minutes) are in `config/upgrade_agent.yaml`.

**Self-edit sessions never touch the user's checkout** (Larry 2026-08-30/31: *"every time we do a self edit we break git — I don't want that happening going forward"*): `SelfEditService.start_session` used to run `git checkout -b <sandbox> main` IN the live working tree, and `submit()`/`revert()` ended with `git checkout main`. A session therefore yanked whatever feature branch the user had checked out (2026-08-30 the entire `macos/` native-client tree vanished mid-build), demanded a clean tree first (the developer deleted a directory to satisfy it), left the running bot importing code that no longer matched disk, and made every OTHER git action taken mid-session — a plan-doc commit, an `mcp_git` push — land on the sandbox branch. Sessions now run in an isolated **git worktree** under `data/selfedit_worktrees/<slug>/` (`git worktree add … -b <branch> origin/main`; the same `data/` home `AppWorkspace` uses for foreign repos): every read, edit, validation gate, commit and push happens there (`SelfEditService.tree`), and submit/revert tear the worktree down (`_remove_worktree`) without a single `checkout` of the user's tree — `verify_appearance` is the ONE method that deliberately reads the user's checkout (`cwd=self.repo_root`), because its question is "what is the human running". Two adjacent fixes landed with it: `mcp_git.logic.push` pushes by explicit refspec (`push -u origin <branch>:refs/heads/<branch>`) and refuses if HEAD moved since the draft — a bare `git push` failed twice live ("upstream branch does not match the name of your current branch") because a branch cut from main inherits `origin/main` as upstream; and a running planner can now be stopped: `POST /api/selfedit/cancel` (also what `revert` does while busy, so "cancel the self-edit" works by voice through the existing `selfedit_revert` tool) sets `UpgradeAgent.request_cancel()`, the edit loop checks it before every planner step, and `_run_agent` settles the job `cancelled` and reverts the session. Cancel is cooperative — a completion call already in flight returns or hits its read timeout first. Also fixed in the same pass: `RunLogger.finish()`'s T4a redaction rebound `reply` inside its closure without `nonlocal`, so EVERY run from 2026-08-28 raised `UnboundLocalError` before finalizing and sat at `status='running'` forever (45 `runlog_write_failed op=finish` warnings; a whole day's runs orphaned at each restart). The existing `tests/unit/test_runlog_store.py` catches it (12 failures) — that redaction commit shipped without running the suite; **run `pytest tests/unit -q` before committing backend changes**, every time.

**Run log investigator** (`mcp_servers/mcp_runlog/`, C1, MORTIMER_MODEL_DISCIPLINE_AND_MAC_SHELL_PLAN.md, 2026-08-17): a read-only MCP server — `runlog_list`/`runlog_detail`/`runlog_stats`/`council_list` — giving the developer sub-agent (the only agent it's wired to in `config/agents.yaml`) a way to investigate its own and other agents' run history and council rounds from inside a delegation, instead of the user having to relay `python -m jarvis.runlog` output back in by voice. Every tool is a thin wrapper over the SAME functions the CLI/sidecar/console already read (`jarvis.runlog.store`'s `list_runs`/`get_run`/`parse_since`, `jarvis.council.council.list_rounds`) — no second query path. `runlog_list`/`council_list` return bounded previews only (`LIST_LIMIT_MAX`/`COUNCIL_LIMIT_MAX = 50`, task text truncated at `TASK_PREVIEW_CHARS`), never a raw payload; `runlog_detail` includes the JSONL `payload_path` for a human to open directly rather than dumping the full untruncated file through the tool result. Class `standard` in `skill.yaml` (not `privileged` — it changes nothing) and no entry in `requires_env`/`requires_keychain`/`scopes`, matching its read-only construction. Its `server.py` needs the same `if __name__ == "__main__": mcp.run()` entrypoint every other MCP server here has — omitting it (as the first cut of this file did) makes the process import cleanly, print nothing, and exit 0 without ever starting the stdio transport, which surfaces at `SkillRegistry.start()` as a same-looking `mcp.shared.exceptions.McpError: Connection closed` on the NEXT server in the list, not on this one — the missing banner in the failing server's own stderr is the tell, not the exception's stack frame.

**App-development**: `mcp_apps` lets the Developer sub-agent scaffold a new private GitHub repo per app (only after user confirmation), tracked in an app registry on the `mortimer-dev` branch. Only `mcp_apps/github.py` should touch the network for GitHub Contents-API calls (`app_create`/`app_write_file`/`app_read`); `logic.py` takes an injected client, matching the pattern used across the other MCP servers.

**App-build engine** (MORTIMER_MODEL_DISCIPLINE_AND_MAC_SHELL_PLAN.md Part D, 2026-08-17): the founding goal — build entire applications by voice, not just scaffold-then-hand-edit-one-file-at-a-time — is a second `UpgradeAgent`-shaped loop bound to a foreign repo instead of Mortimer's own. `jarvis/agents/workspace.py`'s `Workspace` is the seam (`typing.Protocol`: `start_session`/`read_file`/`propose_edit`/`validate`/`submit`/`revert`/`status`/`describe_boundary`) that `UpgradeAgent`'s edit loop (`jarvis/agents/upgrade_agent.py`) was refactored to run against instead of a hardcoded `SelfEditService` — `SelfEditWorkspace` is `SelfEditService` under a subclass with ZERO overrides (D1's own acceptance test is the full pre-existing self-edit suite staying green with no changes), and `AppWorkspace` is the new implementation: a foreign app repo cloned via `git` subprocess (same discipline as `SelfEditService._git` — argument list, never shell, cwd pinned; credentials/owner resolution reused from `mcp_apps.github.GitHubClient`, the one module that already knows how to authenticate) under `data/app_workspaces/<app-name>/` (already self-edit-denied and gitignored, so nothing new leaks into Mortimer's own repo), clone-on-first-build and `git pull --ff-only` on subsequent builds. Validation is manifest-driven, not Mortimer's CI gates: `AppWorkspace.validate()` reads `mortimer.app.yaml`'s `build:`/`test:` command lists from the workspace root; no manifest means "no checks defined," reported explicitly in both the check output and the eventual PR/summary — an unvalidated PR must never be mistaken for a validated one. The write boundary (`_check_app_path`, reusing `mcp_apps.logic.validate_repo_path` for the base traversal/`.git` checks) is a deny-list, not an allowlist: `.git/**`, `.env`/`.env.*`, `*.vault`, and `.github/workflows/**` are always refused — an app-build session must not grant itself CI powers on the app repo — but everything else is writable without a per-file draft→confirm gate, because confirmation happens at the two boundaries that matter instead (starting the build, and submitting the PR), the same two-boundary shape `selfedit_start`/`selfedit_submit` already use. `AppBuildAgent` (same file as `UpgradeAgent`, a subclass with zero duplicated loop code) supplies the three things that actually differ: its own system prompt, the `app_build:` loop-bounds section of `config/upgrade_agent.yaml` (`max_iterations: 40`, `max_session_minutes: 60` — app builds legitimately run longer than self-edits), and `JARVIS_APPBUILD_PROFILE` as its env-level profile fallback, independent of both `JARVIS_UPGRADE_PROFILE` and `JARVIS_PLANNING_PROFILE`. Council escalation rounds it convenes are tagged `workflow="appbuild"` (via `UpgradeAgent.__init__`'s new `council_workflow` param) — `compute_agreement` only excludes `workflow="planning"`, so appbuild rounds are judge-quality evidence exactly like self-edit rounds, no special-casing needed. The admin sidecar owns a fourth async-job slot, `_appbuild_job`/`_appbuild_lock` (same background-thread-plus-polling shape as `_run_job`/`_plan_job`/`_council_job`), deliberately separate from `_run_lock` — an app build never blocks a self-edit run or vice versa — with `POST /api/appbuild/start {app, goal, profile?, plan?, plan_path?}` (`plan_path` read-and-refuse identical to `selfedit_run`'s), `GET /api/appbuild/job`, `POST /api/appbuild/submit`, `POST /api/appbuild/cancel`; unlike `_selfedit_service` (one fixed instance for the one Mortimer repo), the `AppWorkspace` is constructed fresh per job inside the background thread (the app name varies) and stashed on the module-level `_appbuild_workspace` only so the status/submit/cancel endpoints can reach the SAME session the thread is driving. `mcp_apps` gained three thin HTTP-client tools mirroring `mcp_selfedit`'s two-phase convention exactly — `app_build_start`/`app_build_status`/`app_build_submit` — reusing `mcp_selfedit.logic.AdminClient` rather than a second implementation (`TOTAL_TOOLS` is 55: 52 after C1's `mcp_runlog`, +3 here). The developer prompt routes any real-size implementation inside an EXISTING app through `app_build_start` (with `plan_path` when a plan exists), the same rule Part A's self-edit sentence already applies to `selfedit_start` — `app_write_file` stays reserved for small dictated single-file edits. No v1 console panel: status is voice (`app_build_status`) and `GET /api/appbuild/job` only, an explicit scope guard — the Edit panel grew organically from real self-edit use, and the app-build panel should too, once there's real use to grow from.

**LLM Council** (`jarvis/council/`, docs/plans/implemented/MORTIMER_LLM_COUNCIL_PLAN.md, superseded/extended by docs/plans/implemented/MORTIMER_LLM_COUNCIL_V2_PLAN.md): a council may rank, review, and advise on the self-edit loop — it may NEVER author a merged artifact. Cost rises only after demonstrated difficulty: tier 1 (first escalation) fans out to all `economy` profiles as proposers and all `mid` profiles as judges — with a V2 V8 backfill (`COUNCIL_JUDGE_TARGET = 2`) walking the tier ladder upward from `mid` into `frontier` judges when `mid` alone can't field at least two usable judges; tier 2 (a second escalation) adds `frontier` proposers and judges with `frontier` only — **not** `mid`, a deliberate deviation from the plan's original table (`jarvis/council/config.py`'s `TIER_MEMBERS` comment) made to keep proposers and judges disjoint (a model never scores its own proposal) even where tier NAMES would otherwise overlap; `resolve_members`'s `exclude` parameter enforces this per-member, not just per tier name. **Tier-2 frontier partition** (`TIER_PARTITION`/`_partition_judges` in `jarvis/council/config.py`, Larry 2026-08-19): tier 2 names `frontier` for BOTH roles (proposers `["frontier","mid"]`, judges `["frontier"]`), so proposers took every frontier profile and per-member `exclude` then emptied the judge pool; `_fallback_up` cannot rescue it because frontier is the top of `_TIER_ORDER`, so `resolve_members` raised and `convene()` turned that into `_finalize_too_small` — **a second escalation silently declined to convene the council that tier exists for**. Latent since the beginning (the pre-OpenRouter registry of 2 frontier + 1 mid produced the identical zero) and invisible because tier 2 needs two validation failures plus a failed repair to fire. The fix splits the named tier's usable membership between the roles *before* either resolves, applied as an addition to `exclude` (not a filter on the result) so `_fallback_up` and V8's backfill both see an already-restricted pool rather than re-admitting a profile the partition just gave away. Judges are reserved first — a round with no judges cannot happen at all, while fewer proposers merely means less to choose from — but never so many that no frontier profile is left to propose (`min(COUNCIL_JUDGE_TARGET, len-1)`), since tier 2's purpose is frontier *proposals*. The reservation rotates per round, seeded from `round_id` via SHA256 into a local `random.Random` exactly as V4's label shuffle does (one idea applied twice, not two that can drift), because a fixed split would make the same two models the permanent arbiters of every tier-2 winner; **both roles must be resolved with the same `seed` or the split is not a split** — `council.py` passes `round_id` to both calls. The partition basis is deliberately computed WITHOUT the caller's `exclude`: letting it shrink the basis made the judges call reserve from an already-halved pool and yield one judge instead of two.

`COUNCIL_MAX_ESCALATIONS = 2`, tiers strictly ascending, never repeating — a third failure ends the session exactly as it did before this feature existed. Every judge scores every proposal 1.0–10.0 in tenths (`scoring.py`'s `parse_scores`, using V2 V6's stricter regex — `7.44` is now an abstention, not a `7.4`-plus-leaked-justification silent misparse); an unparseable or out-of-range score is an explicit abstention, never silently dropped, matching `jarvis/toolresult.py`'s "never infer from prose what can be recorded as fact" discipline. Proposal labels (`Proposal A`/`B`/...) are assigned by one function, `_shuffle_and_label` (V2 V4: a deterministic per-round shuffle seeded from `round_id` via SHA256, using a local `random.Random` instance — never the global `random` module — so a judge can't infer a proposal's origin from label order). Judge-tier quality (can a cheaper `mid` judge be trusted?) is measured, not assumed: `should_shadow` deterministically (SHA256 of `round_id`, not `random()`) samples a fraction of tier-1 rounds for an additional advisory `frontier` judge pass; as of V2 V7 this shadow pass runs **off the live path**, on its own detached daemon thread with its own `asyncio.run(_shadow_pass(...))` (`COUNCIL_SHADOW_INLINE` is a test-only knob to force it synchronous), so it can never delay `convene()`'s return — shadow score rows land with `shadow = 1` and are appended to the round's JSONL afterward, and are **never** consulted by `select_winner`; every read path filters `WHERE shadow = 0` before selecting. `python -m jarvis.council --replay <round_id> --judges frontier` re-scores a stored round's proposals retroactively (read-only; writes only `shadow=1` rows, or nothing with `--dry-run`), and `python -m jarvis.council --agreement [--since 30d]` reports winner agreement (the primary metric — selection only ever consumes the winner, not raw scores), rank correlation, abstention rate, discrimination by judge tier, and a token-usage summary, then states which promotion branch applies. Promotion thresholds (`COUNCIL_AGREEMENT_MIN_ROUNDS`/`_FLOOR`/`_ABSTENTION_CEILING`/`_DISCRIMINATION_FLOOR` in `jarvis/council/config.py`) are fixed in advance, not hand-tuned after looking at data; fewer than 20 shadowed rounds always means "insufficient data, keep mid-tier," never a judgment call on a small sample — which is also why council retention (`JARVIS_COUNCIL_RETENTION_DAYS`, default 180, V2 V11) is deliberately much longer than the run-log's 30 days: pruning faster than shadowed rounds accumulate would permanently starve that measurement. `config/upgrade_models.yaml` (with its new `tier:` field per profile) stays off the self-edit allowlist — the council's UI membership picker (`EditModePanel.tsx`, `mortimer.council.<tier>` in `localStorage`, matching the drawer's `mortimer.drawer.*` convention) can only narrow which *existing* profiles participate, never define a new endpoint or key. `POST /api/council/convene` and the E3 half of `POST /api/selfedit/reject` no longer block the request for the full round (V2 V5): they validate synchronously, then hand the round to the same `_council_job`/`_council_lock` background-thread-plus-polling shape `_run_job` already uses for self-edit runs, and return immediately (`{"ok": true, "started": true}` / `{"ok": true, "reverted": ..., "council_started": bool}`); `GET /api/council/job` is the polling target. `EditModePanel.tsx` polls that endpoint every 3s (mirroring its existing self-edit run polling) and, once a round settles, both renders the winner card and lets the user expand a "Recent rounds" `<details>` block (`GET /api/council/rounds?limit=10`, V2 V12) to reach any round — including E1 rounds, which happen inside a background agent run and would otherwise be invisible without the CLI. `JARVIS_COUNCIL_ENABLED=false` is the kill switch, enforced at exactly one point (the top of `convene()`) — disabling it costs nothing and escalation falls through to the pre-council report-and-stop behavior unchanged. App-scaffolding has no council integration yet (`mcp_apps` has no validation gate to escalate from) — the module is workflow-agnostic so this can be added later without redesign, but do not invent a trigger for it.

A uuid4 `hex[:12]` staging_id with no digit is ~1 in 200,000 and simply falls back to the pre-existing refusal, which is the safe direction. **Voice isolation Tier 1+2** (`MORTIMER_VOICE_ISOLATION_TIER12_PLAN.md`, 2026-08-21, Larry: *"clean up other voices ... let's implement tier 1 and 2 and then test effectiveness before deciding anything further"*): Tier 1a enables the noise-suppression engines that were already scaffolded in `jarvis/audio/filters.py` (`deepfilternet` default, `pyrnnoise` the measured fallback if the `[ns]` RTF telemetry in `logs/bot.log` exceeds 0.8 — the eval harness decides, not preference). Tier 1b adds `MinWordsUserTurnStartStrategy(min_words=2)` via `LLMUserAggregatorParams(user_turn_strategies=...)` on the `LLMContextAggregatorPair` in `jarvis/bot/pipeline.py` (pipecat 1.4's turn-strategy API — the plan's original `PipelineParams(interruption_strategies=...)` was a 0.0.108 API that does not exist in the deployed pipecat; min_words applies only while the bot is speaking, one word still starts a turn when it's quiet), so a cough or single syllable no longer interrupts Mortimer's TTS — barge-in survival (2026-08-21) already makes any interruption non-destructive to in-flight delegated work, so this is purely about cutting spurious ones. Tier 2 is a local speaker-verification gate: `jarvis/speaker.py` (pure policy + a lazy SpeechBrain ECAPA-TDNN `Encoder`, matching the logic/IO split every other module here uses) and `jarvis/bot/speaker_gate.py` (two `FrameProcessor`s — `SpeakerTap` after the VAD processor computing a cosine score against the enrolled profile on a background thread, `TranscriptGate` after the STT service applying the verdict to final transcripts only). **This is convenience filtering, not security** — a recording of the enrolled voice defeats it, and the policy says so rather than pretending otherwise: an utterance PASSES when ANY of cosine ≥ `JARVIS_SPEAKER_THRESHOLD` (default 0.40), speech < `MIN_VERIFY_SECS` (1.0s — "yes"/"confirm" carry too little voiceprint to judge), no profile enrolled, the model isn't on disk, or the gate hit any error anywhere — fail-open everywhere, because silently eating Larry's own "yes" is the worst failure this feature can have. A dropped utterance is dropped SILENTLY (one log line — deliberately without the text, an unknown speaker's words stay out of the logs — one fire-and-forget `{"type": "speaker_gate", "verdict": "dropped"}` app message, no spoken reply, no UI panel), and `TranscriptObserver`'s `only_from` filter keeps it out of the conversations table too (the memory sweep folds that table into long-term memory; before this filter, live TV dialogue was persisted as USER lines). **Interruptions are gated as well** (`SpeakerVerifiedMinWordsTurnStartStrategy`, same file — added after the first live session proved the plan's transcripts-only boundary (L7) insufficient: the TV never got a transcript through but interrupted Mortimer's TTS constantly): while the bot is speaking, an interruption needs min_words AND a passing speaker score — deliberately fail-CLOSED for interruptions only (a missing score means "not yet", rechecked on the next interim transcription ~1s in; the enrolled speaker's WORDS are still never eaten, L5 governs the transcript gate unchanged). While the bot is quiet the strategy is exactly the plain min-words one, so an unknown voice can still open a turn — its transcript is then dropped and the empty turn dies silently. **The strategy is the ONLY interruption trigger since 2026-08-22**: `DeepgramFluxSTTService`'s `should_interrupt` is now `False`, because `True` made Flux broadcast an interruption on every VAD-level StartOfTurn — before any transcript or speaker score existed — which is the layer that kept letting the TV kill in-flight replies (26 broadcasts/19min measured) while the strategy correctly gated the aggregator one hop downstream; barge-in now fires at first transcript (~0.5s after onset), verified, instead of at VAD onset, unverified (`test_flux_never_interrupts_on_its_own` pins it). The same review fixed `jarvis/bot/interruption.py`'s notifier arming on `UserStoppedSpeakingFrame` — which fires for gate-DROPPED utterances too, so every TV line queued a false "[system] Your previous reply was interrupted" note (measured: 90 notices vs 12 real user messages in one session's final LLM context, the direct cause of Mortimer's clipped, apologetic replies) — it now arms on `LLMFullResponseStartFrame`, so "active" means a reply actually exists to interrupt. `MIN_EMBED_SECS` (0.4s) guards ECAPA against near-empty buffers, whose conv padding otherwise raises. Two voices in the SAME turn share one score (yours passes it, TV text rides along) — separating simultaneous speakers is Tier 4, out of scope. Enrollment is file-based CLI only (`python -m jarvis.speaker enroll a.wav b.wav c.wav`, then `verify`/`status`) — the mic lives in the browser, so capturing enrollment audio through WebRTC was explicitly out of scope. `JARVIS_SPEAKER_GATE_ENABLED` is the one kill switch in this repo that defaults **false** (opt-in until Larry runs the plan's effectiveness protocol and the numbers hold), enforced once in `build_pipeline`: disabled, no profile, or a failed model load all mean neither `SpeakerTap` nor `TranscriptGate` is inserted into the pipeline at all. Camera/face identification (Tier 3) and target-speaker extraction (Tier 4) are explicitly out of scope for this pass.

**Gate V2 — windowed scoring and honest drops** (`MORTIMER_GATE_V2_AND_MODEL_REQUEST_PLAN.md` F1-F5, 2026-08-22, from a log review after "conversation is not natural anymore and in some cases forced" and "many responses not what I would expect and many request just ignored"): a long mixed-audio turn (the user's voice plus background TV blended for several seconds) diluted below `JARVIS_SPEAKER_THRESHOLD` against a single whole-buffer embedding even when a clean segment of the user's own voice was in there — `SpeakerTap._schedule_score` now embeds sliding sub-windows too (`SCORE_WINDOW_SECS = 3.0`, `SCORE_HOP_SECS = 1.5`, capped at `MAX_SCORE_WINDOWS = 8`, plus the whole buffer as a final entry, `_window_slices` returning `[whole]` alone when the buffer is too short) and takes the MAX score across all of them, all inside ONE `asyncio.to_thread` call — chosen over lowering the global threshold because it targets dilution specifically without widening the TV's own score band. **Weather source** (`jarvis/ambient_weather.py`, Larry 2026-08-18 — "let's go with the plan and modify the earlier work"): Weather.gov (`api.weather.gov`, no key, US-only) is PRIMARY, Open-Meteo is the fallback outside the US or on any failure. Kill switch `JARVIS_PROGRESS_UPDATES_ENABLED=false`. **Display windows became independent per-request panels**: a second `surface: "window"` result used to silently REPLACE the first — `web/src/displayWindow.ts`'s single `latest` payload is now a panel registry (`publish()` appends rather than overwrites, `MAX_OPEN_DISPLAY_PANELS = 6` with oldest-eviction and a visible auto-fading toast), and `DisplayPanel.tsx` renders the full stack via an extracted `SingleDisplayPanel` subcomponent, cascade-offset so new panels never land exactly on the last. There remains exactly ONE physical external pop-out window (the Mac shell's native side only recognizes the fixed console/display/drawer roles — `popoutWindow.ts`'s `open()`, `entry.role` is the contract, not an arbitrary per-panel id), so "pop-out works per-panel" means popping any specific in-page panel sends that panel's payload to the one external window and removes it from the in-page stack, not that N panels can each have their own OS window. D41's "never silently lose a result to a blocked/closed popup" fallback is preserved via `restoreLatestAsPanel()`, called on the container's existing popup-liveness poll's falling edge.

**Volatile-state firewall** (`jarvis/memory.py`'s `_is_volatile_state`, Larry 2026-08-18 — "these were never the intent of the memory function in the first place and should not have been saved"): transient repo snapshots (`"19 commits ahead of main"`, `"47 uncommitted files"`, `"Main branch, 32 files modified"`) are rejected at WRITE time, alongside the existing capability-claim scan — a fact that should never exist should not occupy a row, and `git status` answers these correctly on demand so a stored snapshot can only ever be wrong more often than asking. Patterns require a countable NOUN next to the number: the first cut used `\d+\s+(?:un)?committed`, which also matched "Phase 1 committed" and deleted a real decision fact carrying a commit hash — `test_progress_notes_are_not_volatile` pins that. Key hints (`repo_state`, `current_branch`, `uncommitted`, `git_status`) catch the rest.

**Agent discipline** (`jarvis/prompts.py`'s `AGENT_DISCIPLINE`, Larry 2026-08-18): ONE rule block appended to every sub-agent prompt, replacing four that overlapped heavily — `GROUNDING_RULE` (D6), `NO_INVENTED_REMEDIATION_RULE` (D7), the verification taxonomy (skill-library Part B) and `HANDOFF_RULE` (handoff H2). **1,216 chars → 546, a 55% cut with every clause preserved**, each mapped to the observed failure it prevents and pinned by its own test in `TestAgentDiscipline`. The same consolidation move `GOLDEN_RULES` made on Supervisor rules 3/11 rather than appending a fifth. Larry's stated target was "under 15% of the agent's prompt"; that was **arithmetically unreachable and deliberately not adopted** — `S/(S+own) < 0.15` with the scheduler's 490 own chars means 86 chars for seven distinct ideas. The guardrail is therefore an ABSOLUTE budget, `MAX_AGENT_DISCIPLINE_CHARS = 550`, because a ratio is hostage to how terse the agent-specific text happens to be: the developer sat at 23% with the identical rules the analyst had at 76%, purely because it carries 4,037 chars of its own. Post-consolidation the developer is at 11% and the conversational agents at 52-59% — and that residue is a signal about the *thin* agent prompts (the analyst's own text is 382 chars for all web research and weather), not about the rules. **If the budget ever needs raising, consolidate first**; appending is what made this necessary. `test_no_agent_prompt_is_mostly_boilerplate` caps each conversational prompt at 1,200 chars so the block cannot creep back.

**Handoff loop** (`jarvis/clipboard.py`, `jarvis/bot/handoff_tools.py`, `jarvis/agents/delegate.py`, MORTIMER_HANDOFF_LOOP_PLAN.md): an investigation Mortimer cannot finish alone becomes a loop with Larry in it — show a command in the display window, he runs it and copies the output, `read my clipboard` hands it back, the specialist resumes. Built after the 2026-08-18 weather investigation, where run `b74ed019` ran 27 of 28 tool calls successfully and was stopped by the iteration cap (not by giving up), and run `ce0fe118` correctly stated *"I cannot curl localhost:7861/api/ambient"* and stopped there. **The principle behind the reset: the iteration cap bounds unbounded AUTONOMOUS spend, and a handoff is not autonomous** — Larry gates every round — so a handoff resets the budget without limit (Larry: *"quitting is not acceptable"*). Four mechanisms make that safe rather than a loophole: (1) an exhausted-budget run does NOT arm the retry guard (`EXHAUSTED_PREFIX`) — it was an unfinished job, not a failed approach; (2) `continuation: true` is **earned, not claimed** — valid only when the agent's own previous reply contained `HANDOFF_MARKER` ("NEEDS-INPUT:"), which the Supervisor does not author and therefore cannot forge, so an unlimited reset plus a self-declared flag can never become infinite guard-free retries; (3) `findings_path` carries the prior run's conclusions forward through `mcp_repo`'s reader (path confinement and the secret deny-list apply to an agent-supplied path too), read-and-refuse like `plan_path` — without it a reset hands back 15 rounds that get spent re-deriving, which in `b74ed019` was rounds 1-8; (4) `HANDOFF_DEPTH_NOTICE = 4` is a visible honesty checkpoint, never a cap, because a cap is quitting on a timer. The clipboard is **armed**: `clipboard_clear` wipes and arms, `read_clipboard` refuses unless armed then disarms, so Mortimer can only read what was copied *after* an explicit clear — Larry's "clear it first" habit made mechanical, since a habit protects only when remembered. `show_commands` arms as a side effect (H3.4), collapsing a four-step ordered dance into run → copy → read and removing the copy-before-clear hazard. Clipboard text goes into the LLM context via the silent-append path and **never into the transcript**, because `MemoryWatcher` folds the transcript into long-term memory and a password copied moments earlier would otherwise become a durable fact; what was read is shown in the display window instead, which is ephemeral. Deliberately no credential-detection heuristics — a regex for `sk-` false-positives on real terminal output and creates false confidence; showing Larry what was read is stronger. `pbcopy`/`pbpaste` run in the sidecar (which is on Larry's Mac) as fixed argv, never a shell — the safe end of the command-execution spectrum and explicitly NOT a precedent for a general allowlist. Kill switch `JARVIS_CLIPBOARD_ENABLED=false` unregisters the clipboard pair; `show_commands` survives it, because putting a command on screen instead of speaking it is useful either way.

**Skills** (`jarvis/agent_skills.py`, `skills/<name>/SKILL.md`, `config/skills.yaml`, MORTIMER_KNOWLEDGE_FRAMEWORK_PLAN.md K3): the third knowledge layer — authored capability knowledge, in the **Agent Skills open standard** (agentskills.io, open since 2025-12-18) rather than a locally invented format, so a community skill can be dropped in unchanged: a folder with `SKILL.md` (YAML frontmatter — `name` ≤64 chars matching `^[a-z0-9]+(-[a-z0-9]+)*$` and not containing the reserved words `anthropic`/`claude`, `description` ≤1024 chars — plus a Markdown body) and optional `scripts/`/`references/`/`assets/` siblings. Placed between procedures and workflows in `SubAgent._loop` deliberately, and that ordering IS the layer taxonomy: evidence (a procedure, learned, carrying success counters) < reference (a skill, authored, assumed correct, no counters) < requirement (a workflow, normative, with `done_when`), strongest claim read last. Two security properties hold BY CONSTRUCTION, not by policy — (1) **presence on disk is not enough**: a skill loads only if its name is listed under `enabled:` in `config/skills.yaml`, so cloning a hundred community skills into `skills/` enables exactly zero of them, which is Larry's 2026-08-18 "one at a time so the risk can be reviewed individually" rule expressed as a data structure; and (2) **there is no execution path in the module** — nothing imports `subprocess`, `importlib`, `eval` or `exec` (`test_module_imports_nothing_that_executes` greps the source and fails if that changes), so a bundled `scripts/` is detected, reported loudly, declared unavailable in the injected prompt, and never run. Progressive disclosure is real, not decorative: `match_skill` scores the CARD only (name + description, ~100 tokens) and `Skill.body()` reads the file for the ONE skill that matched — `test_matching_never_reads_the_body` pins it, because touching bodies during matching would cost one file read per skill per delegation. `MATCH_THRESHOLD` 0.30 sits between a procedure's and a workflow's; `MAX_INJECTED = 1`; and `MIN_SHARED_TOKENS = 2` (same constant, value and reasoning as `jarvis/consolidate.py`'s — one idea applied twice, not two that can drift) because `_overlap_score` divides by the SMALLER token set, so a short task whose one token appears in a long description scores high on a coincidence: measured 2026-08-18, "what's the plan for today" tokenizes to `{plan, today}` and scored 0.500 against `technical-plan-document` on the word "plan" alone. **An anti-trigger therefore belongs in the skill BODY, never the description** — the opposite of how Anthropic's own skills do it, because theirs are read by a model and Mortimer's are token-matched: adding "what are you planning to do next" to that skill's description as a negative example moved the task's score from 0.000 to 1.000, precisely backwards. `python -m jarvis.agent_skills --explain "<task>"` (mirroring `jarvis/procedures.py`'s `_explain`, DB-free) shows every skill's score, shared tokens, and which one would actually be injected; it is the enable gate — two positive and two negative cases recorded before a name joins `config/skills.yaml`, the negatives mattering more because `MAX_INJECTED = 1` means an over-matching skill *displaces* the one that should have won rather than merely adding noise. Kill switch `JARVIS_AGENT_SKILLS_ENABLED=false` (the `AGENT_` prefix is load-bearing — `JARVIS_SKILLS_*` would read as the MCP skill servers). `python -m jarvis.agent_skills --list|--validate|--from-procedure <id>`; promotion from a procedure is a COPY, not a move (the row keeps its counters and keeps matching), writes a REVIEW-ME body, and deliberately does not enable the result. Larry 2026-08-18 narrowed the one-at-a-time rule to IMPORTED skills only: a skill authored in this repository ships **enabled**, because it is reviewed in its own diff and carries no scripts; `skills/README.md` holds the 7-item pre-enable checklist, whose item 7 is the merge rule — if a draft scores above threshold on a task another skill owns, merge or sharpen rather than shipping a competitor, since under `MAX_INJECTED = 1` the loser of an overlap contributes nothing at all. That rule is also why the proposed `verify-before-claiming` skill does not exist: a general discipline skill loses to every specific one and fires only when nothing specific matched, so its taxonomy went into `jarvis/prompts.py`'s `VERIFICATION_TAXONOMY_RULE` instead — appended beside `GROUNDING_RULE`/`NO_INVENTED_REMEDIATION_RULE`, reaching all five agents with no matching involved. Four skills shipped 2026-08-18, promoted from the five `active` procedures (#18 and #22 were one skill, not two), plus `mcp-server-authoring` authored the same day: `git-history-and-status-review`, `current-weather-with-fahrenheit`, `layered-geolocation`, `technical-plan-document`. Unresolved naming collision: `mcp_servers/*/skill.yaml` still claims the word "skill" against `SKILL.md` — the module is named `agent_skills.py` and the directory lives at the repo root to avoid `jarvis/skills/` (the MCP registry), but renaming the MCP manifests to `server.yaml` remains the open decision (D6).

**Workflows** (`jarvis/workflows.py`, `config/workflows/*.yaml`, MORTIMER_KNOWLEDGE_FRAMEWORK_PLAN.md K4): the fourth knowledge layer and the only one that did not previously exist — authored, normative rules saying how Larry wants a kind of task done and what "done" means. Distinguished from procedures by TRUST, not content: a procedure is learned evidence that earns standing through success counters, a workflow is authored and binding from the moment it is written. Three constraints hold by construction: **authored, never learned** (nothing here creates a workflow from a run — that is `jarvis/procedures.py`'s job, and mixing them would make an unreviewed guess look like a rule); **guidance, not a state machine** (a match is injected as ONE system message, after the procedure hint so the standing instruction is the fresher context; there is deliberately no executor, and `test_workflow_has_no_run_method` fails if one starts appearing); and **explicit before clever** — matching is token overlap against `when:` reusing `jarvis.procedures`'s scorer, no embeddings. `MATCH_THRESHOLD` (0.35) is higher than a procedure's because a false hint costs little while a false rule tells an agent to follow a policy that does not apply; `MAX_INJECTED = 1` because two competing policies in one prompt is how an agent gets stuck. `done_when` is what makes a workflow more than a note. Kill switch `JARVIS_WORKFLOWS_ENABLED=false`, enforced once inside `load_workflows`; a malformed file is logged and skipped so one bad rule cannot disable the rest. Seeded by `python -m jarvis.classify --extract-workflow <key>`, which writes a REVIEW-ME draft and archives the source fact.

**Knowledge visibility** (`GET /api/knowledge`, `MemoryPanel.tsx`'s `.knowledge-layers`, MORTIMER_KNOWLEDGE_FRAMEWORK_PLAN.md K5): one read-only call returns all four layers with counts — memory live/archived/by-tier, procedure statuses, workflow names. The field that justifies the endpoint is `not_reaching_prompt`: on 2026-08-18 the store held 180 facts and ~14 reached the Supervisor, and that was discoverable ONLY by reading a `memory_context_facts_dropped` log line. It is computed by rendering the real context and counting, never by re-deriving the caps, so the number cannot drift from what the prompt actually gets. The console renders it as an amber `.knowledge-warn` line — the one loud element in an otherwise quiet status readout, because silent truncation is the failure this section exists to make visible.

**Conversion layer** (`jarvis/classify.py`, migration `0013_memory_archive`, MORTIMER_KNOWLEDGE_FRAMEWORK_PLAN.md K6): `python -m jarvis.classify` proposes a destination for every stored fact — `keep-memory` / `-> workflow` / `-> skill` / `delete-stale` / `needs-review` — and, like `jarvis.consolidate`, writes NOTHING; each destination has its own explicit key-naming command and there is deliberately no bulk apply. Two rules learned from real misfires: a workflow proposal requires a process VERB **plus** a modal or ordering word (so "prefers Fahrenheit" stays a taste), and only the `preference` tier proposes `-> workflow` outright — measured on Larry's store, every genuine workflow he stated arrived as a preference, while rule-SHAPED `project` facts were a bug report and a feature description, so those go to `needs-review`. `identity` is never auto-reclassified, and ambiguity always resolves to `needs-review`, never to a confident default. Conversion uses `memory.archive_fact(key, became)` (sets `archived_at`/`became`; live reads filter `archived_at IS NULL`) rather than `delete_fact` — on 2026-08-18 an over-deleted fact had to be reconstructed from TRUNCATED console output and its tail is still incomplete, which is not an acceptable recovery story for a layer whose job is moving things between buckets.

**Memory consolidation** (`jarvis/consolidate.py`, MORTIMER_KNOWLEDGE_FRAMEWORK_PLAN.md K2): `python -m jarvis.consolidate` REPORTS duplicate fact clusters and writes nothing; `--drop <key>...` is the only writing verb and names each key explicitly. There is deliberately no "merge everything" command — D2's manual-first decision. Detection is pure (no DB, no model) and reuses `jarvis.procedures`'s `_tokens`/`_overlap_score` rather than forking a second scorer. Two rules are enforced by construction: never merge across tiers (and `identity` is excluded from `CONSOLIDATABLE_TIERS` entirely), and `mixed_content_warning()` flags a fact whose CONTENT covers a topic its KEY doesn't — the 2026-08-18 worked example being `user.location: "Spartanburg (prefers Fahrenheit for all displays)"`, where a key-similarity merge would have silently eaten a preference. Clusters are CLIQUES, not connected components: the first cut used transitive closure and chained 18 unrelated facts on Larry's real store (temperature units + answer length + permission-asking in one group), because a~b and b~c does not mean a~c — `test_clusters_are_cliques_not_chains` pins this.

**Procedures** (`jarvis/procedures.py`, docs/plans/implemented/MORTIMER_MEMORY_PROCEDURES_PLAN.md Part B — never call this concept a "skill"; that word already means "an MCP server" elsewhere in this codebase, see `mcp_servers/*/skill.yaml`). After a delegation finishes, `jarvis/agents/delegate.py` spawns `learn_from_run()` as a fire-and-forget background task: it matches the run's task against existing procedures for that agent (SQLite FTS5 candidate generation over `procedures`/`procedures_fts`, migration `0007_procedures`, plus a Python-side token-overlap score — no embeddings) and either reinforces a match's success/failure counters or, only for a run that actually succeeded with no match, creates a new `candidate` procedure via one small LLM call. A candidate becomes `active` after `PROCEDURE_PROMOTE_AFTER` net successes and stays eligible to be injected as a hint until failures start to outweigh successes, at which point it's `deprecated` (counters keep updating; status never auto-reverts). At the start of a delegation, `SubAgent._loop` runs the same matching function against `active` procedures only and, on a match, injects one short `system`-role hint message before the task. A procedure is a hint only — its description is free text describing what worked, never a replay mechanism, and no confirmation gate is touched by this feature (true by construction: the hint is a prompt message, not a code path). `JARVIS_PROCEDURES_ENABLED=false` is the kill switch, enforced once inside `jarvis/procedures.py` itself. Matching is task-shape-to-task-shape (`docs/plans/implemented/MORTIMER_AGENT_TRUST_PLAN.md` D21/D22): each candidate stores `task_tokens` — the stopword-filtered tokens of the task that created it, written once by `_create_candidate` — and `match_procedure` scores the incoming task's tokens against `task_tokens` (never against `label`/`description`, which is what the hint text still is), using a symmetric overlap ratio (`len(a & b) / min(len(a), len(b))`) so containment scores 1.0 regardless of which side is longer. Rows from before migration `0008` have `task_tokens = ''` and are permanently unmatchable by design (not backfilled — deriving tokens from a summary is the exact vocabulary mismatch this fixed); `DELETE FROM procedures WHERE task_tokens = '' OR task_tokens IS NULL;` is the recommended (not automatic) operator cleanup. `PROCEDURE_MATCH_THRESHOLD` is not hand-tuned — `python -m jarvis.procedures --calibrate` computes it deterministically from the logged run corpus (MATCHED/UNMATCHED score populations by tool-sequence equality, a three-branch percentile rule, clamped to `[0.20, 0.60]`); `--explain "<task>" [--agent NAME]` shows every stored procedure's score and shared tokens against a task for debugging a missed or unwanted match.

## Testing conventions

- `tests/unit/` — one file per module, no external calls, mirrors `logic.py`/service structure.
- `tests/integration/` — MCP-over-stdio, registry wiring, bot wiring; some marked `live` (real external APIs, opt in with `RUN_LIVE=1`).
- `tests/evals/routing_eval.py` — live LLM eval of Supervisor routing accuracy; must stay ≥ 90%.
- `tests/acceptance/` — manual scripted checklists per implementation phase, not run by pytest.
- `pytest.ini` sets `asyncio_mode = auto`, so async test functions don't need `@pytest.mark.asyncio`.

## Known deviations and gotchas

- `DEVIATIONS.md` documents wiring-level adaptations from the original implementation plan — check it before assuming the plan doc (`docs/plans/implemented/Jarvis_Voice_AI_Agent_Implementation_Plan.md`) reflects current behavior.
- Some providers (e.g. Moonshot/kimi-k2.x) only accept `temperature=1`; Mortimer omits `temperature` by default rather than special-casing providers (D-003).
- First bot boot or test run can hang for minutes on a first-time NLTK `punkt_tab` download inside pipecat; see README §7 for the offline workaround.
- `data/jarvis.db` is gitignored and created by `scripts/init_db.py`; don't expect it to exist in a fresh checkout.
- **`.env` is a FILE; `os.environ` is a PROCESS** (MORTIMER_ENV_BRIDGE_PLAN.md, Larry 2026-08-19). pydantic-settings reads `.env` into a `Settings` object and puts NOTHING into the environment; `bridge_settings_to_env` is what copies `JARVIS_DB_PATH`/`JARVIS_TIMEZONE`/`TAVILY_API_KEY` across so MCP children (and `expand_env_vars`) can see them. It used to live in `jarvis/cli.py` and had to be REMEMBERED by every entrypoint that starts a registry: `pipeline.py`, `cli.py` and `test_orchestrator_live.py` did; `tests/evals/routing_eval.py` did not, so every `set_reminder` in that eval died on the literal string `"${JARVIS_TIMEZONE}"` — a `ZoneInfoNotFoundError` five frames deep in a subprocess, naming `zoneinfo` rather than the configuration. It now lives in `jarvis/config.py` and `SkillRegistry.start()` calls it, so no future entrypoint can forget; `setdefault` keeps a real env var winning and makes it idempotent, which is why the three existing calls stay. **The fallback matters as much as the move**: full `Settings` validation fails without OPENAI/DEEPGRAM/ELEVENLABS keys — none of which this needs — so on failure it parses those three names straight out of `.env` (`_dotenv_values`), or a fresh checkout and CI would get no bridge at all and the bug would survive in a different form. Three separate bugs on 2026-08-19 were this one class (two credential probes reading `OPENAI_BASE_URL` from `os.environ`, plus this); in every case the symptom pointed somewhere other than the cause.
- `expand_env_vars` leaves unknown `${VAR}`s as literal text by design — so a `config/mcp_servers.yaml` env entry referencing a variable that isn't guaranteed present hands the child process a literal `"${VAR}"` string. This once gave `mcp-repo` a phantom repo root and made every read report "does not exist" (docs/plans/implemented/MORTIMER_DEVELOPER_AGENT_FIX_PLAN.md RC2). Don't add env entries for optional variables; the child inherits the full parent environment anyway, and `_repo_root()` in both `mcp_git`/`mcp_repo` now ignores `"${"`-containing values as defense in depth. `mcp_reminders`'s `_tz()` gained the same defence 2026-08-19 (a `"${"` value is treated as UNSET, falling back to UTC with a warning, rather than raising), and `SkillRegistry._start_server` now logs one `mcp_server_env_unresolved` WARNING naming the server and the variable — a warning, not a refusal, because refusing would turn a degraded reminder into a dead voice loop.
