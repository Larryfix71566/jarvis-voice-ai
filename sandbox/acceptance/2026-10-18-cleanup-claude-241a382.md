## Mechanisms verified sound from the diff

- **Child-creation vs. deletion race (core WS-28 fix):** `Images.create` (`sandbox/images.py:108-120`) now registers the task directory + `state.json` under the same `start.lock` that `Controller.destroy` (`sandbox/control.py:434-454`) holds for the full delete. Mutual exclusion on this single lock correctly serializes "new child appears" against "parent gets deleted" in both directions — confirmed by the logic paths exercised in `test_verification_child_reserves_parent_before_reclamation` and `test_verification_child_refuses_if_parent_deletion_won`.
- **Lease isolation (vs. initial 24206281):** `Pruner.deletion_guard` (`sandbox/prune.py:172-183`) only appends `session.lock` to the lease list when `owner["task"] == task`, and all leases are acquired with `LOCK_EX | LOCK_NB` (`sandbox/prune.py:192-196`), never a blocking wait. This correctly avoids both (a) locking unrelated sessions and (b) classic lock-ordering deadlocks against any mutation code that acquires `session.lock`/`files.lock` before `start.lock` — non-blocking acquisition sidesteps ordering entirely rather than depending on it.
- **Fail-closed state integrity:** state mutation (`status="deleting"`) happens *inside* the `guard()` context (`sandbox/control.py:448-454`), so if `deletion_guard` raises before `yield`, `ExitStack` unwinds cleanly and no partial state is written — matches `test_busy_mutation_locks_retain_old_stopped_tasks` et al.
- **`runner_fingerprint` scope extension** (`sandbox/verify.py`, adding `prune.py` to the hashed file list) is narrow, correct, and directly tested; no concerns.

## Blocking finding

**Finding 1 — Malformed-record scan in `deletion_guard` has host-wide blast radius, reintroducing the class of bug WS-28 was meant to fix.**
`sandbox/prune.py:173-188`

```python
for record in sorted((self.controller.home / "sessions").glob("*/session.json")):
    ...
    raise SandboxError("Cleanup cannot establish session ownership")   # line ~175/179
for record in sorted((self.controller.home / "tasks").glob("*/state.json")):
    ...
    raise SandboxError("Cleanup task record is malformed")             # line ~188
```

Both loops scan **every** session and **every** task on the host, unconditionally, before any filtering to the candidate `task`. A single malformed/symlinked record *anywhere* — unrelated to the task currently being destroyed — aborts `deletion_guard`, and since `Pruner.run()` calls this guard for every candidate in its plan, it blocks cleanup of **every other, otherwise-eligible task** on the same invocation and every subsequent one until the offending record is removed.

This is directly demonstrated (and currently encoded as expected behavior) by the final sub-case of `test_malformed_ownership_cannot_grant_orphan_cleanup` (`sandbox/tests/test_prune.py`): an unrelated task `aaaabbbb0007` with a corrupted `state.json` is created, and the test asserts that pruning of the completely unrelated, legitimately-idle task `aaaabbbb0006` is also blocked (`self.deleted == []`).

The stated goal of this repair was that "final code leases only the candidate owner" (fixing 24206281's all-session-lock blast radius). That goal is achieved for **lock contention** but not for **data corruption**: a stray/partial write to any `session.json` or `state.json` (e.g., from a crashed process, including a crash during this very creation/cleanup code) permanently wedges reclamation host-wide, with no self-healing path, until an operator manually inspects and removes the bad file. Given the explicit review scope includes evidence retention and cleanup reliability, this is a concrete availability risk worth flagging as blocking even though it is evidently deliberate (comment: "A malformed ownership record must not become an orphan grant") — the design choice should be an explicit, signed-off risk acceptance, not an incidental side effect. A narrower mitigation (e.g., a per-task ownership marker that doesn't require scanning unrelated records, or isolating malformed-record failures to only the tasks they could plausibly reference) would preserve the fail-closed intent without the full-host blast radius.

## Flagged, non-blocking observations

1. **`start.lock` couples all new sandbox/verification-child creation to in-flight deletions for up to the 120s delete timeout** (`sandbox/control.py:448-454` holds `start.lock` through `self.command("delete", ...)`; `sandbox/images.py:108` now requires the same lock for registration). This appears to be the deliberate cost of closing the creation/deletion race, not a defect, but it's a new latency coupling that didn't exist before this diff (previously creation was unlocked) and is worth confirming is acceptable for the verification-child path's latency budget.
2. **The `tasks/*/state.json` scan in `deletion_guard` (`sandbox/prune.py:184-188`) validates only that each record is well-formed JSON** — it never reads `parent_task` to check relevance to the candidate being deleted. Protection against deleting a parent with a live, conflicting, or ambiguous set of children therefore depends entirely on the unmodified `plan()` method (not present in this diff), which this review cannot verify independently.
