## What the frame-time number is, and is not

Frame = one camera step, `CACurrentMediaTime()` from `MemoryGraphStore.setCamera` until the render server ran the completion block of the explicit `CATransaction` that carried it. Inside: a 0.5 ms-timeout main run-loop pass (SwiftUI commit) and the transaction commit/flush (layer display). Ten warm-up steps are not recorded.

- The Canvas is rasterised by SwiftUI's RenderBox (`RBDrawingLayer` → `RBImageQueueLayer`, recorded in the JSON's layer survey), with `rendersAsynchronously` at its default `false`. [likely] that rasterisation completes inside the transaction and is therefore inside the span — the documented meaning of synchronous presentation, and the span responds to drawing complexity (2.06× the trivial-graph control). It is not proven by a screen capture: `CGWindowListCreateImage` is unavailable in this SDK and ScreenCaptureKit needs Screen Recording permission for the test runner. If Larry wants that stronger evidence, a ScreenCaptureKit latency test is a C8 hardware-acceptance row (one-time permission for `xctest`).
- The `cacheDisplay` bitmap used for the pixel checks is a CoreGraphics re-render of the layer tree and costs ~760 ms p50 on this graph; it is reported in the JSON and is not on the on-screen path (no production code calls `cacheDisplay`/`bitmapImageRep`/`ImageRenderer`). The first harness attempt had this inside its span, which is why it read 163 ms.
- The 0.5 ms run-loop timeout can only inflate a frame, never shorten it.
- Hardware, OS, scale (window backing 2×, camera fit 1.57, zoom 0.5×–4×), dimensions and method are in the JSON, as the plan requires.
