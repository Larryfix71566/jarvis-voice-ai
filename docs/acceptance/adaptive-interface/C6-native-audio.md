### What the diagnosis cost, and what it found

The first built-in-mic run **failed**: residual +34.3 dB, 9 user turns, 0.69 dB of reduction. Three wrong turns are worth recording because each was settled by a measurement rather than an argument.

- `engine.start()` failed with `kAUInitialize` (-10875) under VPIO. `--probe` (seven graph shapes, fresh engine each) showed why: after `setVoiceProcessingEnabled(true)` the input bus reports 9 ch / 48 kHz and the **output** bus 0 ch / 0 Hz, and `mainMixer → output` with `format: nil` inherits that and fails; every shape with an explicit output format starts. Hence reading both hardware formats *before* enabling VPIO and connecting the output explicitly.
- My first explanation of the echo failure — the `input → mainMixer` (mono 48 kHz, muted) connection forcing the bus to one channel — was **wrong**: the failure reproduced identically on the tap-only graph. It was then isolated by single-variable runs (A2 removes the concurrent wake engine; A3 additionally removes the in-process VPIO-off phases and lengthens the settle; CH re-runs the bench's own graph in the same minute as a room control): the cause is the **concurrent second `AVAudioEngine`**, nothing about the graph. The graph is still the tap-only shape and is proven to cancel, but whether the muted mixer connection also cancels is **untested** — the version of that file was never committed and the tap-only patch overwrote it; reconstructing it and re-running this bench is what would answer it. (The `--graph-ab` run that was meant to answer it compared against HEAD `0419f50`, which predates the output-format fix, so both its VPIO-on phases failed to start and it settled nothing.)
- The `--channels` run answered the other half: with VPIO on, all nine channels of the input bus carry the **same** processed signal (idle 0.00086 vs 0.00083 RMS during playback on every channel), so the 9→1 downmix was never the problem. `CaptureConverter.firstChannel(of:)` takes channel 0.

**§3.5 — the plan's "no change to the wake listener" is refuted.** `JarvisClient.updateWakeListenerRunState()` runs the listener exactly while `state == .connected && !micEnabled`, i.e. on top of the transport's VPIO engine, and `WakeWordListener.startCapture()` opens its own `AVAudioEngine`. Measured, that costs the transport its cancellation (row "wake, legacy" above) **and** the wake engine receives nothing at all on the built-in mic (`wakeRMS` 0 in every VPIO-on phase; on AirPods it did receive audio, so the deafness is device-dependent, the cancellation loss is not). Larry chose the fix on 2026-09-13: feed wake from the transport's tap. `AudioEngineIO.onMonitorPCM` fires for every converted buffer whether or not capture is enabled (wake runs while muted) and is installed only while a monitor exists, so with wake off a muted mic costs no conversion at all; `NativeAudioTransport.setCaptureMonitor(_:)` installs it on the live session and clears it on teardown; `JarvisClient.feedWakeAudio(_:)` hops to the main actor and calls `WakeWordListener.feed(_:)`, which is ignored unless the listener was started with `WakeAudioSource.external` — so audio can never arrive twice. The listener also gained a `WakeSocket` seam (the shape `NativeAudioTransport` uses for `NativeSocket`), which is what makes any of this unit-testable. The WebRTC path keeps `.ownEngine`, unchanged. The wake detector now receives echo-cancelled audio, which is better input than it has ever had; N10 rule 4 (pause while the bot speaks) is left exactly as it was.

**Discarded runs, for honesty:** the first built-in-mic session had a television audible in the room (Larry said so) — those numbers are not used. The earliest runs used a speech-shaped *noise* signal, which Silero never scores as speech whatever the level; they were replaced by real `say` speech before any conclusion was drawn.
