### Retained lifetime independent of a request permit

At proof activation create one owner-issued lifetime record, retained strongly by the connection record and every associated peer, pending media item and queued output. It contains an opaque unique lease/epoch token, the exact connection-record identity, full immutable `SessionBinding` key (owner/device/grant/session/login incarnation/host and grant/session/process generations/scopes), fixed proof wall and monotonic deadlines, and monotonic retirement state. A new record or reused session/peer string never reuses this token. `ProofContextVerifier` still requires the exact request permit/context/current worker; this retained record is **not** a new credential or a way to manufacture that permit.

Every proof-owned peer stores this lifetime plus its peer incarnation, resource identity and service token. Queued output additionally captures these exact identities. Missing/mismatched/retired lifetime denies proof-owned peer use; absence of a request permit can never turn that check into true. Existing explicit fake/v2/v3 peers retain their established path and do not acquire proof authority through a default. Do not overload the current permit-only `_proof_lifetime_current()` fallback as the peer check.

`tick`, `emit_output`, `drain_output`, cached voice receipt validation and final activation/publication must check the retained record against the paired F-protected clock image and its fixed deadlines, independently of any request permit. Only wall **and** monotonic comparisons passing can authorize use. A legitimate wall rollback cannot increase the monotonic deadline. Clock-image inconsistency remains terminal. `emit_output` checks before content preparation, again at enqueue and after authority acknowledgement; `drain_output` checks the captured lifetime before dequeue and after acknowledgement before returning bytes. Any retirement/expiry during preparation or ACK prevents new payload publication. Queued items are inert immediately when their lifetime retires, even if physical cleanup is pending.

An owner maintenance poll while idle observes virtual clock expiry and initiates the same retirement path without waiting for another phone request. All authorization gates still compare deadlines directly, so delayed polling is never a grace period. With unchanged or rolled-back wall time and monotonic time advanced to expiry, no peer operation, output enqueue, output dequeue or response publication succeeds. Snapshot/card behavior outside the voice resources is preserved; voice cleanup must not blindly delete another connection's shared card view.

### Retirement, cleanup handoff and exact ownership

Use a two-stage retirement protocol. The first stage is a short registry/host transaction: mark the lifetime retired, invalidate its reply seal, set its existing cancellation event and retain one pending cleanup descriptor. This immediately stops new admissions, send admission and proof-owned output use. The descriptor captures the exact lifetime/connection epoch, full binding, known attachment/ledger identities and broker-ticket owner token. Each lifetime also has a worker/R-owned attachment index: every peer or pending resource created by a frozen continuation is registered there even if retirement was already requested. Cleanup reads that index only after the current continuation finishes, so a resource created after the initial descriptor is not missed. It compares each captured peer incarnation/resource/service-token identity at deletion. No descriptor contains a callback. Neither `claim`, disconnect, `end_send`, expiry polling nor an ASGI caller may touch SQLite, peers, resource dictionaries, output queues or tickets directly.

The descriptor is handed to a **separate bounded maintenance mailbox** owned by `_AuthorityChildServiceHost`, not appended to its one-slot request queue and not submitted recursively. One descriptor is coalesced per lifetime; at most the existing 64 connection records may remain active or retiring, and a record retains its capacity slot until cleanup, in-flight completion and pending-send completion are all accounted for. Filling the request queue cannot drop or postpone the mailbox behind fresh ordinary work. Host admission checks and the worker's dispatch loop inspect maintenance first; an idle worker uses a bounded wake/poll (at most 20 ms) so retirement after `invoke()` cleared the permit still runs without another request. After the current frozen operation settles, the worker processes retirement before taking another ordinary request. If a descriptor is published after that check, the wake/poll path still observes it. Cancellation removal of a queued request cannot remove the maintenance descriptor.

The worker performs only exact-match local cleanup: it compares the current peer object, resource object, peer incarnation, service token and retained lifetime/full binding with the captured descriptor before removal. It clears the matching owner lease only if that lease still names the same peer/resource. It discards matching pending media and queued output across registered sinks by the same identities. Extend the existing sink's local cancellation helper to accept exact binding/incarnation/lifetime filters for proof-owned cleanup; cancellation by peer string alone is forbidden here. A later peer/session incarnation with reused IDs, or another owner, survives stale cleanup. The store's new owner-thread discard API removes only this lifetime's matching broker tickets; no connection-close session revocation or global signout is introduced.

Cleanup has one nonextending **real monotonic five-second deadline**, measured from first retirement; repeated disconnect/claim failure cannot reset it. If host drain already exists, use the earlier deadline. A single host maintenance watchdog may observe mailbox deadlines and trigger existing host terminal fencing/anchor close if the worker cannot finish; it cannot perform store/resource cleanup itself. For ordinary v4 owners this requires the new bounded terminal path specified in the correction below; anchor closure alone is not a child-reap guarantee. Failure records uncertain cleanup, never a successful local cleanup receipt. This includes a worker stalled in a native operation or login-seal retirement. No global process census or unrelated-process termination is introduced.

During quiescing, descriptors join the owned quiesce cleanup instead of creating new user work; all exact local resource/ticket cleanup occurs before DB close and before `_drained` can become true. A quiesced worker may not acknowledge drained while a descriptor, frozen continuation or owned send remains unsettled. A closed worker's already verified complete quiesce can satisfy a later duplicate retirement; a dead/fenced worker without that receipt requires the corrected bounded ordinary-owner terminal/reap outcome and cannot pretend the mailbox ran. Pending ASGI sends keep their existing cancellation/join ownership until `end_send`; no early record deletion or late egress is allowed. Existing admission failure handling at accept/response callers remains unchanged.

### Locks and linearization points

Names: H host lock; C connection registry lock; L login clock/coordinator lock; F paired service clock; G native/store authority; R service runtime; Q bounded output sink. Preserve existing owner/readiness gates before F. No condition/event waits, callbacks, native I/O or login retirement occur while H/C are held; nested local mutex critical sections are bounded and contain no blocking work. In particular, **never acquire L while holding F**, and never acquire H while already holding C.

| Phase | Lock discipline / effect |
| --- | --- |
| Phone retirement / close / handoff / send admission | H → C for registry state and descriptor intent; release both before publishing a host wake or doing any other work. Claim additionally holds F outside H → C to validate its deadline. Existing C-only callers must be reorganized so none call a host API while holding C. |
| Mailbox transfer | H alone captures/coalesces immutable descriptors, then releases H. Worker checks C alone if needed to capture the exact record; releases C before R/store work. No H/C → R or H/C → G nesting. |
| Voice authorization / ticket / activation | Owner/readiness → F → G, then R only for bounded local peer/effect changes. The native observer's existing G → H acquisition remains short; it releases H before returning, with no C/R acquisition in that callback. Never enter G with H/C held. |
| Lifetime snapshots | F → H → C captures exact active/retired/deadline facts, then releases H/C before G/R work. Hold F across the corresponding effect guard so authoritative clock updates cannot race it. A disconnect may still set cancellation meanwhile; already-authorized continuation may finish privately, but post-effect registry validation must withhold publication and schedule exact cleanup. |
| Output publication | Under F/G, validate peer/resource identity under R, release R, then H → C → Q performs final retained-lifetime/cancellation check and queue enqueue/dequeue. This introduces no H/C → R edge. Proof-owned peer mutations are serialized on the worker. The last post-ACK F → H → C validation controls return of dequeued bytes; bytes already returned before retirement are in flight, not recalled. |
| Local cleanup | Worker takes R (and Q for exact output removal) without H/C/F/G; then releases R/Q before store-local discard. No authorization is acquired because cleanup only decreases local authority. After those steps, acknowledge the descriptor under H → C. Login-seal retirement takes L **alone**, with all other locks released, and must complete or fail within the original cleanup budget. |

| Watchdog | H → C only to publish terminal admission/cancellation, then releases locks before anchor close; it never takes L/F/R or touches SQLite. |

A native grant acquired before retirement can belong to the existing authorized frozen continuation. Retirement never confers permission to publish. Clock expiry is checked at the actual mutation guard under F; connection retirement is checked before and after effect, and at every enqueue/dequeue/claim/send-admission boundary. No success can emerge after terminal host failure. Containment/cleanup does not imply rollback of an acknowledged effect.

The existing v4 drain protocol allows only `service.commit` acquisitions after quiescing. **Do not widen it.** If drain starts after initial authorization but before ticket issuance/consumption begins, locally abandon the broker intent and discard any issued ticket without a new grant. If issue is already in flight, finish/settle that operation, then discard locally rather than starting consume. If consume acquired before drain, its acknowledged result may reach a remaining path requiring only the existing bounded `service.commit` continuation; otherwise settle/clean up. If another authorization/read grant would still be required, do not omit that validation or acquire a forbidden grant: abandon the effect before activation, or fence/settle uncertainty if the outcome cannot be established. Drain does not promise successful completion of every admitted voice operation; its deadline and truthful drained/uncertain outcome remain mandatory. A race rejected by the existing native observer remains terminal/uncertain as currently specified. Reaching authorization alone is not permission to invent new ticket grants during drain.

### Receipt states after worker completion

The ledger retains the full binding/RID/payload digest and originating lifetime identity; retire it by exact entry identity, never by RID or session string alone. Capacity/tombstones remain bounded by the existing 256-per-binding / 4096-total ledger; capacity exhaustion denies before a new ticket. Do not evict a live/uncertain/retired entry merely to permit same-RID reissue.

| --- | --- |

### Ticket deadlines, store ownership and bounded retention

The new broker ticket metadata is optional and all-or-none; existing explicit-ticket calls remain unchanged. The service supplies an exact opaque broker-owner token tied to the retained lifetime, full binding key and immutable timing record from the trusted worker. Store issue/consume validate exact types and matching ownership/binding; phone JSON cannot supply this metadata. Construction records the store's owning thread; broker-tagged issue/consume and local broker reclamation require that thread, while untagged legacy call behavior is preserved. No helper may mutate `store._tickets` from the connection layer or event loop.

At broker preparation capture paired monotonic time `m0` and proof deadline `P`. Set `T = min(m0 + 30,000 ms, P)`; this deadline never changes. Also capture a real-monotonic deadline capped by the same remaining interval at preparation, before any issue grant can stall. This real-time ceiling prevents a stalled synthetic clock image from extending the maximum 30-second bound. The existing wall expiry remains bounded by the 30-second store rule and proof wall expiry, but wall time alone never authorizes broker consumption. Store consume checks **both** the trusted paired-monotonic sample and its own current real-monotonic time at the point immediately before setting `consumed`, after authority acquisition. Equality at either deadline expires. A wall rollback, repeated issue attempt or delayed native grant cannot reset either deadline. Neither time source nor the timing record is caller-selected phone data.

F is released between completed issue and the next consume phase, so legitimate paired clock advancement is observed. Recheck before media preparation and final activation; retained proof lifetime governs the peer thereafter, not a newly extended ticket. If pre-consume checks detect expiry/retirement, discard the issued ticket locally and produce the appropriate known denial without calling consume. If a race is detected inside the trusted consume call, preserve its existing terminal owned failure behavior; do not catch-and-resume to obtain conformance.

The store adds a narrow local discard method taking broker-owner token, exact full binding and optional exact ticket handle. It can only delete matching broker-owned entries, cannot create/reset/consume tickets, cannot touch SQLite/anchor/session/grant state, and cannot affect legacy untagged tickets. It takes only the store's local lock after checking its construction thread, never a new native grant; this makes cleanup usable during quiesce without bypassing authorization. Wrong thread, malformed ownership metadata or a present foreign entry supplied as an exact target is an error; it must not silently delete any entry. An already-removed exact target or an empty owner sweep returns zero, making repeated retirement idempotent. The service uses only this API.

There is at most **one broker ticket record outstanding in this single-worker host**, including the current operation's consumed-but-not-yet-cleaned record. Reserve this local slot before issuance; a second/reentrant broker intent is rejected before issuance. After a known consume ACK, discard that record before media preparation and retain anti-replay intent in the existing ledger/lifetime rather than an ever-growing consumed-ticket list. After known expiry, cancellation or failed preparation, discard it on the worker before settling; uncertain native outcomes fence and retain at most that one record until owner cleanup/reap. Retirement descriptors also sweep any matching leftover record using the store API. Tests must create and retire more than 64 successive connection lifetimes and many distinct RIDs to prove raw broker ticket count returns to zero, not just that higher-level records disappear. The ledger remains capacity-bounded and never treats discarded ticket storage as permission to reissue an existing RID. No claim is made that legacy explicitly injected tickets have acquired this new brokerage retention policy.

### Executable ordinary-v4 failure path

1. At the original five-second retirement/cleanup deadline (or the earlier active drain deadline), the Python host watchdog publishes terminal admission/cancellation and settles waiting callers with bounded `authority_unavailable`/uncertain completion. It releases H/C before closing its authority endpoint. It does not wait for the blocked worker, acquire L, or manufacture a cleanup/drained acknowledgement. The exact-resource mailbox result remains incomplete. This is a caller-failure bound, not proof of child exit.
2. Endpoint EOF/error makes the native owner leave its normal `serve()` loop. It closes/shuts down the native endpoint and enters **ordinary-v4 terminal cleanup unconditionally for this ordinary lifecycle**, including EOF/protocol errors and nominal shutdown. The entry condition is version 4 with no restore-hold lifecycle, not `restoreHoldRequired`. It uses only the child PID returned by its own successful `posix_spawn`, with one sole reaper for that child. It never sends `restore.prepare`, writes pending/stable recovery state, creates a recovery journal, or sets a restore-hold flag to obtain cleanup. The existing normal shutdown ACK, if already received, is evidence only of that protocol step; it does not replace reap.
3. Start one absolute owner cleanup deadline from `ProcessInfo.processInfo.systemUptime`. Budget **at most 2,500 ms** after terminal-loop exit: healthy shutdown may receive up to 250 ms grace; abnormal EOF/error receives zero grace; TERM gets at most 250 ms; KILL gets at most 2,000 ms, truncated by the remaining overall deadline. Each phase uses `waitpid(ownedPID, ..., WNOHANG)` and short deadline-clamped polling. Every EINTR retry and final check rechecks the absolute deadline. No ordinary-v4 path falls back to blocking `waitpid(..., 0)` or extends the deadline after a signal/retry.
4. Before signalling, establish from the sole reaper's nonblocking wait result that this is still its unreaped child. If the exact PID is returned, save status and do not signal again. A zero result means the child is still waitable/running: send SIGTERM only to that PID; if the TERM phase expires, send SIGKILL only to that same still-owned child and poll until the overall deadline. Never signal a process group, sibling, arbitrary PID or PID after ECHILD/unknown ownership. ESRCH is not a reap receipt; follow it with the bounded exact-child wait. Signal or wait errors must not be converted to a successful exit.
5. A reap is confirmed **only** when this sole waiter receives the exact owned PID with exit status. Then record the native outcome before closing the singleton descriptor. A nominal clean child exit may preserve normal success status. Any forced signal, unexpected child status, missing shutdown/cleanup acknowledgement or earlier terminal service error remains a non-success lifecycle result even though the child was successfully reaped. Physical reap never upgrades an uncertain media effect, withheld reply or failed drain to success.
6. If the deadline expires without verified reap, or wait ownership becomes uncertain (including ECHILD), enter an explicit **fenced-held** native state: keep the singleton lock FD open, forbid child restart/new admission, retain the failure outcome and do not return through the descriptor-closing defer. Do not continue signalling an uncertain PID. A dedicated held-error path may block while retaining the lock; this is deliberately not reported as a bounded successful reap. The caller has already received bounded failure. Normal kernel-responsive TERM/KILL cases must demonstrate actual reap inside the 2,500 ms budget. Kernel inability to prove exit cannot safely be hidden by releasing the singleton or promising unconditional process termination.

The five-second Python cleanup deadline and the native 2,500 ms cleanup budget describe separate phases. Expected responsive-kernel terminal cleanup therefore has a bounded caller failure followed by bounded native escalation/reap; do not claim the child is necessarily reaped within the original five-second caller deadline. Actual process tests record both elapsed intervals plus EOF-to-owner-cleanup entry. Arbitrary OS scheduler suspension is not a new successful receipt. During an ordinary non-socket Python lock stall, the independent watchdog closes the endpoint and the native owner is waiting on that channel, so this path is executable without the stalled worker cooperating. A socket-send/receive error path must also converge on the same cleanup routine.

The singleton lock remains held throughout grace, TERM, KILL, reap verification and any fenced-held uncertainty. The child inherits its existing lock FD; its death alone does not release the owner's FD. There is no normal-v4 owner return until verified reap, and no replacement owner admission while the old child is alive/unverified. A normal owner may release the lock and exit after confirmed reap without entering a restore hold. Existing restore/recovery hold requirements continue separately and must not be weakened by sharing helper code. Version 1/2/3 behavior stays unchanged by this narrowly versioned correction.
